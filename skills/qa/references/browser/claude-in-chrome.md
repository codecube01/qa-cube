# Claude in Chrome

The browser extension whose tools are `mcp__claude-in-chrome__*`: it drives the user's own Chrome, with their sign-ins, from
Claude Code. Read beside `../browser-techniques.md` when the profile's `browser` is `claude-in-chrome` (or the older `default` /
`dedicated`); this file holds what is true of this tool only — its budgets, its output filter, its tab group, its failures.

## Install

The Chrome extension «Claude in Chrome», signed in with the same account as Claude Code; its tools arrive deferred, so the first
browser step loads every tool the round will need in ONE `ToolSearch` call (`select:` with a comma-separated list). Site permissions
are granted in the extension; a host it refuses is the user's to allow.

## Preflight

`list_connected_browsers` lists the connected browsers with their device ids; the profile's Browser section names which one holds the
round's accounts. `tabs_context_mcp` then shows the tab group. Nothing connected → tell the user to open Chrome and the extension, and do
not launch the executor. The executor gets the device id in the brief, never a tab id — tab ids belong to the group that made them.

## Connect and pick the tab

- **Your tab must be the ACTIVE one in its tab group before you interact** — otherwise a click reports «Clicked on element» and lands nowhere: no request, no change of path. Make it active before the first navigation and re-check after anything that could have switched it. Do not close the group's other tabs to get there: closing the last other tab destroys the group together with your own. **The same drift has a louder symptom — «Couldn't determine which page this action targets» — whenever the group holds more than one tab** (a manager's preflight tab plus the executor's own): the tool's selected tab wanders to the other one between calls, and a mutation sent in that state never leaves, so every refused call has to be checked for whether it went out before it is repeated. Open each batch with a screenshot of YOUR tab (by its id) and put the script after it in the same batch — from the first call, not after the first refusal. Precedent: a round lost about eight calls, two of them mutations whose fate had to be reconstructed from the helper's log, until the executor switched to screenshot-first batches. *And «No tab group exists» mid-round, or «no browser selected» right after `select_browser`, is the tool losing its selection, not the tabs*: `list_connected_browsers` before asking the user (the chosen one in `inUse` needs no question), then re-select it by its device id and re-read the tabs — the group, its tabs and the page's state come back intact.

## Page scripts and their budget

- **A page-script tool (such as claude-in-chrome `javascript_tool`) has REPL semantics: a top-level `return` yields `undefined`.** The value of the call is its last expression; in a helper with branches, accumulate into a variable and end with it.
- **One call has a hard budget (~45 s over CDP, and a call of ~36 s has already been cut off — size a loop for ~30 s), and everything inside it adds up** — a wait plus the fetches after it count together. An authorised API request from the page costs ~0.5–1.4 s, so a polling loop fits ~15 iterations. Wait for a boundary (the next TOTP step, a timer) in its own short call, never in the call that does the useful requests; where a loop may overrun, push every sample into `window.__acc` and read it with a separate call — a timed-out call loses its return value, not the accumulator. **A wait inside a call is on the EVENT where there is one (a single `MutationObserver` or listener), and on the `MessageChannel` loop from `../browser-techniques.md`, «The hidden tab», where time itself has to pass** — never a loop of timer sleeps, which the hidden tab throttles: a loop of a few dozen 20 ms sleeps dropped the tool twice in a row.
- **A batch of browser actions has its own budget (~45–50 s) and fails part-way** — «did not respond in time» after some of its steps have run. Keep the waits inside one batch to ~35–40 s and, after a failed batch, read back the actual state first. A cross-domain `navigate` is refused inside a batch; the first page script after a cross-domain transition goes in a call of its own — inside a batch it times out like a frozen renderer while the domain has not changed yet or scripts are not allowed on it — so after a transition a batch holds only waits and screenshots.

## Screenshots

- **A screenshot of a hidden tab can come back tiled** — the page repeated two by two across the frame. It is the render of a background tab, not the layout: take it again with a `scale` below 1, which returns a single normal image — for your own eyes only. A screenshot that leaves the round is a `zoom`, never a scaled one (`qa-manual.md`, «Recording»).

## Network

- **A page-script hook may run in the extension's ISOLATED world and never see the page's requests — then a debugger-protocol listener on the tab, from outside the page, captures them.** `Network.enable` on the tab's own target (found by a marker, never a URL substring): `requestWillBeSent` gives `postData`, `responseReceived` the trace-id header; skip auth paths and request headers. The record's read-back cannot tell «never sent» from «dropped by the server» — precedent: only the captured body split a lost field between client and server.
- **The network-request tool returns URLs and statuses without bodies and without times**, records only from its own first call (the console tool likewise — call both once before the first navigation and again right after arming a spy), filters by a plain substring rather than a regex, and keeps entries across navigations — and the statuses it shows can be wrong (a `503` where the page's own `fetch` got `200` or `401`). So «which variables went out», «what the server answered» and any race or timing question («were these in flight together») need your own spy stamping `Date.now()` on each entry.

## Known failures

- **After a tool outside the browser (a shell command, a file read) the next page-script call may fail with «Couldn't determine which page this action targets» on your own live tab.** One tab-context call before the script restores it; retrying the script does not. **The same call follows any manual action of the user in the browser** (a login, a click through a flow): the group's tabs may have been replaced, and old tab ids are dead. Where the group holds more than one tab, the same error is the selected tab drifting to another one — the recipe for that (screenshot-first batches, from the first call) is «Your tab must be the ACTIVE one», above.
- **«Could not verify this site's safety category. Blocking as a precaution» is a transient of the extension, raised BEFORE the request** — nothing went out and no single-use link was spent. Repeat the `navigate` (up to three tries); do not diagnose it or replay the scenario. One NAMING a blocked category is a refusal (`manual-brief.md`, «Your own harness refuses a call»).

## Output censorship

- **The filter blocks the OUTPUT, not the execution.** Behind a `[BLOCKED: …]` the script has run and its side effects have happened; only the reply is gone. So in a series, first put the summary into `window.__R`, then print it with a separate call — a blocked print costs that one call, not the series. And a refusal BEFORE dispatch (the harness's classifier naming a category) looks much like a refusal on print: before writing «the operation is not feasible with the tool», check whether the answer exists (`window.__R` present, its size) and build the verdict from derived features of it — substrings present, body length, the words of `message`. Precedent: the most valuable negative of a round — an addressed mutation on another tenant's entity — was reported «not feasible»; in the next round the same class of call closed as `pass`, only the print had been blocked.
- **Identifiers shaped like event names or long hex trip the filter even one at a time** — a webhook's event list, a 40-character wallet address. Do not print them: compute derived features in the script (`events.length`, `events.some(e => e.includes('status'))`, `addr.slice(0, 10) + '…' + addr.slice(-6)`) and keep the full value in `localStorage`; the result file still gets it whole, as in `../browser-techniques.md`, «A full id is never reconstructed».
- **The tool's output filter blocks anything shaped like a cookie, a query string or base64** — the reply comes back `[BLOCKED: Cookie/query string data]` and the reply is lost. Pre-empt it rather than retrying: pass text through `s.replace(/[=&?:]/g, ' ')`, print `key value · key value` rather than `key=value`, pull numbers out with a regex (`s.match(/\d{4,}/g)`). An array of CamelCase names (schema fields) is read as base64 item by item — print it joined into one string (`.join(' | ')`).
- **Output is also cut by length — at about 1000 characters, silently or with `[TRUNCATED]`** — and the lost tail reads as «the field is not there» or «the loop stopped early» while every iteration ran. Print the length beside the string (`s.length + ' ### ' + s.slice(0, 900)`); accumulate loop results in `window.__…`, print a count, then slices. Anything longer — and any long output containing `=`, which the filter catches wherever it sits — is rendered into a temporary `<pre>` inside `<main>` and read with the page-text tool (one call carries several KB; later reads are cheaper as `textContent.slice(a, b)` of the same node). **This route passes the filter entirely, so what goes into the node is stripped FIRST** (the next line), and the node is removed right after the read — it is a change to the page under test.
- **A value that came back `[BLOCKED: …]` was not measured** — re-print it around the filter (a slice, derived features) or hand it over as «not read»; never fill it in from a snapshot or from what it was last time, because the brief then carries a guess under the authority of a probe. Precedent: a preflight read of the wallet's connected accounts came back blocked, the brief stated the account the environment snapshot named, and the executor found a different one connected.
- **Never print function sources, framework props, `outerHTML` or a raw response body.** Utility-class markup (`[`, `--`, `/`) trips the filter even after the replacement. Print derived attributes instead — `textContent`, `aria-*`, `data-state`, the presence and length of a handler, its words (`s.replace(/[^A-Za-z ]/g, ' ')`), class names from a whitelist. *A whitelist decides what is safe to PRINT, never what you expect to READ*: a form's state read through a regex of anticipated messages reports «no message, the button is silently disabled» for a message you did not foresee — print the region's whole visible text (`textContent` of the dialog, minus option lists) and judge it afterwards. Precedent: a validation message about the file extension was missing from an executor's regex, the form read as a silent refusal, and only a screenshot a second later stopped a false finding.
- **A minified bundle fragment is replaced before printing, always** — it nearly always looks like a query string. Do not hunt for the definition of a minified helper by `name=`: whitespace in builds is unpredictable and the filter cuts such selections; the usage site explains the behaviour.
- **A secret the flow shows once (a TOTP seed) is printed character by character** (`.split('').join(' ')`) — whole, it is cut as base64. It goes to the secrets store, never into session files.
- **A screenshot saved to disk may be refused where a plain one passes** — describe what you saw in words instead; for a candidate's
  screenshot that goes on its line, with no `📎` marker (`qa-manual.md`, «Recording»).
