# Writing the findings and the report

Read at step 6 of `../SKILL.md`, before writing `99-report.md`; the wording entries are read again whenever a finding is being
shortened for the tracker. Each entry is a situation a finding lands in and the line that decides whether it survives contact
with the customer; the precedent that closes an entry is what paid for the rule. **Read the file whole** — a finding withdrawn
after delivery burns its id and forces edits to the report, the registries and the knowledge base, and the entry that would
have prevented it is never the one you were looking for.

## Contents

**Is this a finding at all**

- a candidate enters the findings table only with the violated requirement QUOTED — a gap, a blocker or a latent defect goes to the second table, a wish to side findings
- a requirement whose SURFACE is missing — one order: a live carrier task, another layer with no carrier, this task's own scope
- a known defect blocked the target scenario — it stops being background and enters the findings; one caused by the environment, not the task, goes to side findings
- the task's goal (its user story) gets a verdict of its own — «tried and failed» is not «not covered», an incomplete «full matrix» is a fail
- a `pass` that holds only because today's data hides a mechanism already known to be wrong — a latent finding, filed now
- a `fail` on an attribute of a requirement — check the neighbouring tab, column or block first
- «the capability is missing» — not a defect until a requirement for exactly this carrier is found
- «the data is gone» on a test environment — first a question about a cleanup, then a finding
- a consequence the task's own text predicts — scoped by the contour it lands in, not by the mention
- development decided an item in a comment — not a finding: «Closed by a development decision», its premise measured; a scope a comment left open «Awaiting the analyst's decision» (a gap in the TEXT stays in the second table)
- the same statement in its IMPLICIT form — the one that gets missed
- a compound finding over several FRs — reconciled against each FR separately, and quoted from the spec
- reconciling covers your own past rounds too — an artifact on the environment that PROVES your finding is the signal; a closure a neighbouring session declared covers only the halves it measured
- a guard you could not satisfy — not a defect until the legitimate caller fails it too
- «there is no requirement for this» expires when a new source of requirements turns up — re-open the burned ids
- a CAUSE read off one sample of client-side state — checked against the library's code in the served artifact before publication
- a `pass` of the form «the other side changed state» — rests on a signal from that side, not on the client's own state
- «no check was found» is the phrasing of a finding that was never probed — and «the consumer cannot see this», settled by the response already in hand; «accepts what it should check» waits for whoever checks LATER
- a plausible explanation that leads to the right conclusion — its CAUSE is still verified, because the cause is what the team acts on
- what belongs to the task's report and what to the side-findings registry

**Setting the priority**

- «will the user see it today» — and two calibrations colliding on one finding
- a security finding: severity against the standard, and the bypass proven by a symmetric before/after set

**Wording a finding**

- a finding about appearance names the conditions of observation — width, zoom, locale, theme
- «the wrong HTTP code arrived» — filed only with proof that the right code does reach the client
- a finding read off a NUMERIC CODE — name the dictionary, and prove the mapping by behaviour
- the title line is the dedup key, so it carries the where and the when
- **The first bold sentence** — compression may not make it false · the plain verdict before the cause · the requirement's terms, not the surface's · a spec word and a quantifier both smuggle claims in

**What «not covered» is allowed to claim**

- «no access to X» is a claim about a fact — verified by trying, not inherited; a browser `403` is not proof, and a surrogate oracle carries the line naming what it cannot show
- «X is broken», concluded from an unsuccessful search — a protocol of the attempt, and it may not enter the profile or the knowledge base as a property
- «the design has no such screen» — true only of the canvas you opened; and a frontend round with no design comparison says so

**The table's own mechanics**

- **The table is written to be copied out whole** — a stray `|` breaks the row · HTML dies in the tracker · what stays out of the cells · the split by layer comes before the ids, and one defect or two decides the number of ids · an inherited row may have acquired a task · text on screen needs a screenshot or the bundle's own string

## When the customer has to file the finding by hand

**Where the session's tracker access is read-only, a finding destined to become a task is delivered as a ready-to-paste issue file, not only as a row in the report.** The report's cell is written to be read — compressed to a business sentence, capped in length, stripped of the measurement trail on purpose. A tracker task needs the opposite: the steps in order, the identifiers, the trace ids, the control experiment, the expected-versus-actual pair, the root cause. Someone has to convert one into the other, and when writing to the tracker is the customer's job, «someone» is the customer — who has neither the session nor the evidence. So produce the file in the session folder next to the report, one per finding, shaped by the tracker's own bug convention (title `Area \ what \ under what condition`, environment and date of reproduction, steps as a table, expected/actual, cause), with the finding's id INSIDE the body, not only in the file name — the customer pastes the body and the file name stays behind on disk, so the next round's «is it filed» search by id (below, «The table's own mechanics») finds nothing and reports a filed finding as absent from the tracker. Say in the delivery that the files are ready to paste. Two riders. Keep one file per defect even when the defects share a root cause — a single task with two clauses gets closed on the first, and the second clause is the one nobody re-checks; say in the file that the sibling belongs in the same DoD instead of merging them. And once the tasks exist, the findings table is rewritten: filed findings leave the table for a line below it with their task links, and their session ids are consumed. Precedent: a round's two findings sat in the report for the length of the delivery, and the customer's next message asked for exactly these files — the conversion work had been left on the only person who could not do it. The issue file obeys «what stays out of the cells» (below) like a cell does: before delivery, grep it for the `sessions` path and the knowledge-base path from the profile — the result must be empty.

## Is this a finding at all

**A candidate enters the findings table only together with the requirement it violates, QUOTED — the executor's candidates are raw material, not the table.** Before an id is assigned, answer three things per candidate. Can you quote the clause it breaks (from the task or the spec section, verbatim)? Yes → the findings table; a requirement addressed to a component that does not exist is quoted and fails like any other. No quote, and the candidate is still the task's business → **the report's second table, «Findings without a violated clause»**, in the same cell format, priority scale and id numbering: a **requirements gap** (the spec is silent or contradicts itself — the Requirement column quotes what the text does say, or names its silence), a **known defect that blocked a requirement's verification** (the column quotes the blocked requirement, the cell names the defect's own task), a **latent defect** (the column quotes the requirement that passes only by today's data). Keeping them apart keeps the first table's claim exact — every row in it breaks a clause the customer can read — while the second table still reaches the tracker, as its own block. Does the cell need the words «not required by the spec, but…» to stand? Then it is a wish, not a defect: side findings. Does it lean on another task? Name that task in words — what it delivered and in what status — and for a closed one say «its DoD does not cover this», never «we address new requirements to it». Precedent: of eleven candidates in scope, six survived these questions; three moved to side findings and two were withdrawn with their ids burned, after the report, the registries and the knowledge base had all been written.

**A requirement whose SURFACE is missing is sorted in one order — who owns the missing part decides where the row goes.** The shape: the requirement is accepted, the round measures what it can, and the part that would show or carry the result — a screen, a consumer, the other layer's half on a layer-labelled task — does not exist. Take the questions in this order and stop at the first yes. (1) **Is the missing part the subject of its own live task (not done)?** → a line UNDER the table, «no surface, the carrier is <task> (<status>)», with what was measured; no id, since it would duplicate planned work, and never this task's blocker. (2) **Does it belong to another layer, with no task carrying it?** → the second table, a requirements gap for the analyst: «no task carries the <layer> half of FR-N». (3) **Is it within this task's own scope?** → a FAIL of the requirement in the findings table (the entry «A requirement addressed to a component that does not exist», below), its priority set by «will the user see it today». In all three the requirement's verdict row still reads `partial` or `fail`. And whatever the carrier task would NOT fix keeps its own id whatever the answers — data lost on a surface that already exists, a wrong value the API already returns. The order replaces three rules that sent the same row to three places (a line under the table, a side finding for the other layer, a numbered finding); its precedents are those of the entry below and of the container entry in `planning.md`.

**A known defect that blocked the target scenario stops being background and goes into the findings — the second table — with an updated rationale.** In the
brief such defects are usually listed as «not findings of this round» — but if it is exactly the one that prevented a requirement from being
closed, staying silent about it means hiding the reason for the gap: it goes into the report in a new role («blocks the verification of X»),
and the decision on its priority is the manager's, asking the user if necessary. Precedent: the executor hesitated over whether they were
entitled to raise a background defect that had become the main result of the round's first half. **Where the defect is CAUSED by the
environment — a client, a device mode, a third party's configuration — rather than by the task's code, its origin decides, not the
requirement it surfaced on**: even when it produces an observable fail of that requirement, it goes to the side-findings registry, and the
task's report carries it as a line outside the table and as the REASON the requirement is not covered, not as its `fail`. The origin is
proven, not assumed (the served build holds no route that could produce it). The goal verdict (the entry below) is a separate layer and does
not move: the row reads «not covered — cause: <the environment, proven>», the goal reads «not confirmed» with that cause listed. Precedent: a regression item «signing works as before» failed
visibly, the cause turned out to be a mode of the signer's wallet, and the customer moved the finding out of the task.

**The task's goal — its user story — gets a verdict of its own, stated before the requirements table, and it is never dissolved into the
count of closed criteria.** A round can close most of the acceptance items while the one thing the task exists for — «as a user I want to
do X» — never once succeeded; counting progress by items buries exactly that. Three rules follow. **«We tried and it did not work» is not
«not covered»**: the first is an acceptance result and belongs in the findings and the summary, the second is a gap in coverage, and a
reader takes «not covered» to mean «not looked at» — the one exception is a failure whose cause is PROVEN to lie outside the product (the
entry above), and there the row names that cause in words. **A requirement of the form «the matrix is passed in full» with an incomplete matrix is
`fail`, not `partial`** — partial completion does not meet a requirement about completeness. **An obstacle outside the product** (a broken
extension, a missing device) is not charged to development, but it does not cancel the goal verdict either: the finding takes the half the
product is to blame for, and «the goal is not confirmed», with the causes listed, stays in the summary. Precedent: 23 of 34 spec items
closed, and no operation ever went through with any client but one — the manager put it under «not covered», and the customer asked for the
goal's verdict.

**A `pass` that holds only because today's DATA hides a mechanism the round already knows to be wrong is a latent finding, and it is filed in the round that saw the mechanism — not left as a caveat on the pass.** The shape: the executor establishes how the thing works (a list re-sorted on the client over only the loaded page, a total summed over the visible rows, a match on a prefix that happens to be unique) and notes that on the current records the output is still right. The verdict then reads «pass, with a caveat», which is true and is exactly the wrong artifact: the caveat lives in the result file and the knowledge base, the requirement row is green, and nobody re-measures a green row. The collection grows, the coincidence ends, and the next round has to report a regression of a requirement that was never actually met — with the customer reading it as something the latest build broke. Two moves. Name the condition that would break it, and look for it in the data NOW (an object created early and changed late, a second page, a duplicate prefix): where it already exists, the pass was never a pass. Where it does not, the row is `partial` with the mechanism as the reason, and a finding is filed in the second table at the priority of the damage once the condition arrives — the mechanism is the defect, the data only postpones the symptom. Precedent: a default sort order was accepted as a pass on the note «the client re-sorts only the loaded page; on today's data the page boundaries are not crossed»; a month later the collection had grown by half, the order broke at the seventh position, and the retest had to present as a new regression what the first round had already described in words.

**Before assigning a `fail` on an attribute of a requirement — check whether it is covered by another part of the screen** (a neighboring
tab, a table column, a different block). The answer is usually already in the result a line below: the executor describes what they actually
saw, and turning that into a verdict on the requirement is the manager's work — and that is exactly where «but here it is» gets lost. And
**if the executor marked «needs an analyst's decision on what counts as X» — that is a signal that there may be no defect at all**: first
the interpretation is chosen (with a rationale), and only the interpretation «the requirement is not met» yields a finding with an ID.
Otherwise the item is filed as a question for the analyst without a number — withdrawing it later costs more than never filing it.

**«The capability is missing» is not a defect until a requirement for exactly this carrier has been found.** A function absent from a
neighboring cabinet, from another role, on another platform or in another client is checked with two questions: (1) is there a
task/requirement for exactly this carrier — search its own repository and tracker, not just the task you are testing; (2) was it ever there
— a control experiment on a build without the task. Both answers «no» = a missing capability, and its place is the side-findings registry as
a question for the product, not a Major in the task's report. Precedent: «the partner cabinet has no column selection» moved from Major
into the registry — no requirements for that frontend exist at all, and the control was not on the old build either.

**«The data is gone» on a test environment is first a question about a cleanup, and only then a finding.** Before filing a defect of the
kind «the system no longer shows what used to be there» (entities vanished, totals dropped, history was truncated), ask the user or the team
whether there was a maintenance operation: test environments get cleaned and migrated without announcements, and from the product's side
that is indistinguishable from data loss. The sign that makes the question mandatory: what «disappeared» is exactly what had previously been
considered non-working or obsolete. Precedent: a Major explained by «a projection without a backfill» was in fact a bulk deletion made the
day before — the finding was withdrawn after delivery, burning an id and forcing edits to the report, the registry and the knowledge base.
The orchestrator was silent about it, too: maintenance cleanups are done around it, so «there are no traces in the logs» is not proof.

**A consequence the task's own text predicts is still scoped by the contour it lands in, not by the mention.** Analysis-style tasks often
list the side effects of the change they propose («after the rename the journal will hold both generations of names»). That sentence makes
the effect *expected*, not *in scope*: it will be fixed in the journal, by whoever owns the journal, on a different task — so it belongs in
the side-findings registry with a line in the report pointing at it. Ask the contour question of **every** candidate, including the one whose
mechanism the task describes itself; a mention in the description is the easiest way for a neighbouring-contour finding to slip into the
table. Precedent: two audit-journal findings were correctly filed as side findings while a third — the one the task had predicted — went into
the table on the strength of that prediction, and the customer moved it out.

**A comment in which the implementer declares part of the work out of scope is a statement about SCOPE — and a comment goes stale claim by claim, never as a whole.** Such comments are the cheapest context in the round and the easiest to mis-handle in both directions. Treat the whole comment as authoritative and you write off requirements the accepted task still contains, on the say-so of the person whose work you are checking. Treat it as noise — or, the common failure, stamp it «outdated» wholesale because a later build refuted some of it — and the findings it governs go out framed as oversights when the team had already decided them, which is the version that costs trust: the customer reads a defect report about a thing they scoped out weeks ago. The discipline is flat: split the comment into its claims and verify each against the environment. **A surviving decision — «we do it differently», «skipped on purpose», «left as is» — is a valid decision on the requirements, not a deferred question, and the item it covers is not a finding.** It leaves the findings table for a section below it, **«Closed by a development decision»**: requirement · the decision (quoted, with its date) · what the round measured. The measurement stands next to the decision and does not contest it — it answers a different question, whether the decision's PREMISE holds; where it does not (the alternative the decision offers leads somewhere the answer is not), that is reported as a fact beside the decision, for the customer, and the item does not return to the table. The requirement's verdict does not move with the item: a requirement left unmet stays `partial`/`fail`, with «development decision, see below» in place of a finding id; a finding that already carried an id from an earlier round keeps it in the section's text, and the id is burned, not reissued. **Where a comment addresses the item but leaves open whether it is deferred, dropped or still owed**, the question goes to **«Awaiting the analyst's decision»**, below the table too, stated plainly. The boundary with the second table is the source of the doubt: «Awaiting» holds questions about SCOPE that a comment opened; a requirements gap — the spec's own text silent or self-contradictory, with no comment on it — stays in «Findings without a violated clause» with its id and «needs an analyst's decision» in the cell. The counts in the summary, the tracker comment and the session registry exclude the closed items, and in the tracker comment the section shrinks to one line: «the comment of <date> is taken into account». Get this wrong in either direction and it costs the same round trip: leave it in the table and the team is handed a defect report about work they decided weeks ago; drop it entirely and the requirement it leaves unmet vanishes from the verdicts. Two riders. The vocabulary of such a comment is evidence in itself: an implementation the author calls a placeholder or a generated draft, still wired to a live operation, is a sharper risk than the same screen described neutrally — quote their word. And comments are re-read every round on the task **and its parent**: an item's own modification timestamp usually does not move when a comment is added, so «nothing changed since last time» says nothing about the discussion. Precedent: a two-comment thread was marked «outdated» as a unit because its first comment (about a contract) had genuinely been overtaken by a rebuild; the second declared two of the round's four Majors to be separate tasks and stayed true word for word across two rounds — it reached no findings table at all, and when it was finally reflected, the customer's next correction was that those two findings did not belong in the main table either. Precedent: a decision «instead of our own holder search, a link to the external explorer» was accepted as closing its item, and the round's measurement showed the explorer cannot enumerate that role's holders at all — reported beside the decision as a fact for the customer, not as a finding.

**The same statement usually arrives in its IMPLICIT form, and that form is the one that gets missed: a comment naming which findings are being fixed says just as much about the ones it does not name.** «Fixing 25, 26, 27» against a filed list of six reads as a retest instruction — which findings to go and check — so the round plans itself around it and never asks what the sentence says about the other three. It says they are out of the current scope, exactly as an explicit «these are separate tasks» would, and every consequence of the entry above follows: the unnamed items leave the findings table for «Closed by a development decision» (the decision: not in this fix), their requirement verdicts unchanged, and where the comment leaves open whether they are deferred or dropped, the question goes to «Awaiting the analyst's decision». The cheap test at step 1, wherever a comment enumerates work: **count the named items against the filed list**, and where the two differ, write the complement into the plan as a scope question rather than as three more retest rows. Getting it wrong is not a wording problem — the report hands the customer what looks like an incomplete fix, when what actually happened is that the team fixed everything they undertook to fix. Precedent: a retest round verified all six findings, reported three fixed and three «reproduce without changes» in one table, and the customer's correction was immediate — the developer's comment had named three, so the other three were never in the fix.

**A compound finding covering several FRs is reconciled against each FR separately** — a caveat in one item («or a recovery
code») does not extend to its neighbor; and on a retest, quote the requirement from the spec rather than from the previous
finding's wording. Precedent: API-1 merged FR-5 and FR-6, the developer fixed exactly what FR-5 requires, and «the remaining
half» under FR-6 turned out to be behavior per the spec — the round-2 executor, having inherited the wording, filed it as a
defect. The absence of a server-side check of an invariant that the spec only required to be «displayed» is a **requirements
gap** with an explicit «needs an analyst's decision», not a violation of that requirement.

**Reconciling a finding covers your own past rounds, not only the tracker — and an artifact on the environment that proves the finding is the signal to go looking.** The reconcile rule is written against the tracker, so that is where it gets applied; a QA repository's own registries (the session index, the side-findings file, an older campaign's defect list) are read at step 1 for context and never consulted again at publication time. They should be: a defect the team never filed is exactly the defect that survives into your round, and re-discovering it as news costs the report its authority — the customer remembers the earlier run even when the tracker does not. The reliable trigger is a specific shape of evidence: **the environment already contains the artifact your finding produces** — a file of a forbidden type, an entity in a state the product should not allow, a record with an impossible value. Somebody put it there, on purpose, to prove something; on a shared QA environment that somebody is usually a previous round of yours, and that round wrote down what it found. Check before publishing, and where a past record turns up, the finding changes shape rather than disappearing: not «we found X» but «X was recorded on <date>, no task was ever filed, it still reproduces, and here is the part that is new». That sentence is stronger than the discovery it replaces. Precedent: a round filed a Critical for a missing server-side format check, having proved it with a direct probe; the same defect sat in the previous campaign's defect list from two months earlier — and the foreign `.exe` and `.txt` files in the client's record, which the round had used as supporting evidence and described as being of unknown origin, were that campaign's own test uploads. The mirror case, on a regression or bundle round: a block that a recent neighbouring session already closed is filled by transfer with an explicit mark «from session <X>, <date>, build <Y>; not re-verified in this round», and its findings are referenced, never copied into this round's table.

*And a finding CLOSED in passing by a neighbouring session is closed only for the halves that session measured* — the per-FR split of a compound finding above, applied to its closure. Such a closure arrives as one sentence in someone else's report («the blocker of the other session is fixed»), measured against the finding's headline symptom, and from there it is copied into the registry and the knowledge base as «fixed». Before it is recorded that way, re-read the finding's original cell and check each of its halves against what the closing session actually observed; an unmeasured half keeps the finding open, narrowed, under its own id. Precedent: a finding «activation starts no check, does not register the record with the external provider, does not turn the follow-up tracking on» was declared fixed by a neighbouring round that had seen the check start; two weeks later the retest found the provider request still carrying no tracking at all, and the registry, the knowledge base and the neighbour's report all had to be corrected.

**A guard you could not satisfy is not a defect until you have shown that the LEGITIMATE caller cannot satisfy it either.** The mirror image of the entry below, and it arrives with more force behind it: the round spent real effort — dozens of attempts, every variant of the mechanism, a self-test proving the tooling computes correctly — and every one was refused. That trail reads as thorough evidence, and the candidate writes itself at the top priority, because the thing refusing is the feature under test. What the trail actually establishes is that *this caller* was refused, which is what a working guard is supposed to do. The discriminator is cheap and usually already in hand: find one execution of the real thing — a processed event in the queue, a delivery in the log, a record only a valid call could have produced — and if it exists, the guard admits legitimate traffic and the finding dissolves into a blocker of the ROUND, addressed to whoever owns the credential or the contract. Say it that way in the report, plainly, including the sentence that the mechanism works: it is the difference between handing the team a false alarm about their security check and handing them the one question that unblocks the next round. The rule generalises past signatures — an authentication you cannot pass, an allow-list you are not on, a rate limit you keep hitting. Precedent: an executor proposed a Blocker reading «the supplied secret validates no webhook at all»; acceptance found four vendor events processed by that same endpoint the day before, reclassified it as the round's own blocker, and the report asked for the signature contract instead of filing a defect.

**A verdict of «there is no requirement for this» is only ever true of the requirements you have READ — so when a new source of requirements turns up, the burned ids and the analyst questions are re-opened, not left where they were.** Items closed that way are the quietest part of a report: a candidate finding is downgraded to a question, its number is burned, and the round moves on satisfied that it behaved conservatively. That conservatism is correct at the time and expires the moment a second spec appears — a subtask's engineering brief, a linked decision document, a design note — because such a document is written by the people who had to implement the thing, and it routinely legislates exactly the corner the first spec left silent. So make it a step of the round that finds the new source: walk back through everything closed as «requirements are silent» and re-rate it against the new text. Expect the result to be asymmetric — some questions get answered and stay questions, and some come back as findings, usually stronger than the original candidate, because a violated clause beats a gap. Precedent: a candidate withdrawn as «the spec says nothing about this state» was re-rated against a subtask's spec found two rounds later, where a corner case demanded precisely the opposite behaviour; it returned as a Critical, and in a wider form than it had been withdrawn in.

**A finding whose CAUSE is inferred from one reading of client-side state is published only after that mechanism has been checked against the library's own code in the served artifact.** The shape is quiet and reads as thorough: the executor observes an effect, opens the browser's storage (a key, a cookie, a cached entry), sees a value that explains it, and writes the explanation into the finding as its mechanism — «the key is not updated when X happens, and restoration reads that key». The effect may well be real; the mechanism is a guess about who writes that value and when, made from a single sample, and it is the half the reader acts on. It is also the half the customer can refute in one move, because reproducing it is the first thing they do — and a refuted mechanism takes the whole finding with it, since nothing else in the cell survives without it. The check costs one grep of the bundle that already sits in the round's evidence: find the write and the read in the library's code, and say which is which. Where the code contradicts the sample, the finding is withdrawn rather than reworded, and the observed effect moves to a line of its own — «observed once, cause not established, closed by this re-measurement» — which keeps the fact without the claim. Two riders. The same discipline covers **the reproduction recipe** handed to the customer: a recipe is a claim about the product, and a step phrased as an oracle («check the key — it has not changed») that was never measured breaks in their hands on the first attempt. And withdrawal is the expensive direction — it edits the report, the registries, the knowledge base and the project map at once — so the grep before publication is always cheaper than the correction after it. Precedent: a round filed a Minor saying a stored «last connector» key is not rewritten when the user switches through a menu, and that the page therefore restores the wrong one; the customer's first reproduction showed the key updating, and the library's own code in the served bundle put the write inside the very call the menu makes. The finding was withdrawn, its id burned, and the effect it had been built on stayed open as an unexplained single observation.

**A `pass` of the form «the other side changed state» rests on a signal FROM the other side — the client's own state proves only what the client believes.** The mirror of the entry above, and it hides in green rows rather than in findings: a wallet switched its network, a remote peer accepted, a counterparty applied the update — the executor reads the application's store, sees the new value and the gate lifted, and writes `pass`. What the store records is the client's own model, and a client can update it locally without the other side ever being asked; an absent request then gets explained away («not needed, already approved») instead of being read as the tell. So a claim about the counterparty's state names the counterparty's own evidence — an event it emitted, a request it answered, a read taken through its side — or it is written as «the client believes X». Precedent: a round passed «the network is switched from the menu» on the client's state plus the note that no request to the wallet was needed; the next round armed a recorder on the wallet's own events and saw the wallet re-announce the old network six seconds later — the published pass had to be re-rated, and a neighbouring task's closed finding with it.

**«No check was found» is the phrasing of a finding that was never probed — and it is the tell to grep your own report for.** A claim that the system does not validate, does not enforce, does not reject is a statement about behaviour under an input the product's own surface refuses to produce: the form filters it out, the client blocks it, the control will not accept it. So the executor measures what they can — the surface — and completes the picture from neighbouring evidence: another field with no server-side check, foreign records on the environment that could only exist if the check were missing. The conclusion is often right, which is exactly why it survives review; but it is inference, and the report presents it as observation. The probe that settles it is usually one call that goes around the surface, and it pays twice — it either turns the finding into evidence or dissolves it, and on the way it answers whatever «how did that get here?» question the round had parked. The discipline: whenever a candidate finding contains «not found», «no sign of», «apparently absent», either run the bypassing probe or write the honest «not measured» instead. Precedent: «the server does not validate the file format» rested on a client-side measurement plus two foreign files of a forbidden type sitting in the data; three direct calls confirmed it outright and, in the same pass, proved those foreign files had arrived through the ordinary path rather than some other contour — which was the question the round had opened and forgotten. *The mirror form, «the endpoint ACCEPTS what it should check», is not a finding until you know who checks it and when* — synchronously, a worker minutes later, the external system at execution: an accepted value that a worker rejects twenty minutes on is a working asynchronous check (the read-back rule is in `qa-manual`). Precedent: an accepted bogus transaction reference was nearly filed as unvalidated; old records showed the worker failing such requests within minutes.

**The same claim in its cheapest form — «the consumer cannot SEE this» — is settled by re-reading the consumer's own response, which the round is usually already holding.** A finding that says a fact is hidden from a role (the customer, the integrator, the operator) names a surface the round did not go to: the executor measured through the administrative contour, saw the fact only there, and completed the sentence from where they happened to be standing. Unlike the entry above it needs no new probe at all — a round that exercised the whole flow has the consumer's own payload in its log, three steps earlier, and one grep for the field name decides it. Skipping that grep is expensive out of proportion to its cost, because «invisible to X» is the load-bearing noun of the first sentence: if the field is in fact served and merely secondary, the finding does not shrink, it inverts — from «X has no way to know» to «X can know, but only by asking again, and the headline fields keep saying the opposite», which is a different claim addressed to different people. Check the timestamp too, so the response you read is one taken **after** the change, not the interim snapshot that predates it. Precedent: a round reported that a cancellation was visible only in administrative fields the consumer cannot reach; the consumer's own response, in the round's own run log and dated after the correction, carried all three of those fields — the finding survived only as a question about notification, and every artifact built on the original wording had to be rewritten.

**A plausible explanation that leads to the RIGHT conclusion is still checked — the team receives the cause, not the conclusion.** A customer or a colleague offers «it is shared, because this instance serves only our product»; the premise checks out, the conclusion checks out, and the sentence goes into the report whole. But a correct conclusion is compatible with several causes, and the fix follows the cause: from the wrong one the team is told to change the thing that does not matter. Spend the one or two calls that establish the mechanism before the explanation is published as the reason. Precedent: «one role dictionary, because the identity server serves one product» — the dictionary was indeed one, but by the server's own design it is shared per tenant regardless of how many products it serves; the wrong cause implied «add a second product», the real one «add a second tenant».

**What goes into the task's report and what into the side-findings registry.** The «in scope» criterion is **the letter of the task's
requirements, not the topic**: a defect that does not follow from the text of the requirements (even one found in the same feature and the
same service) goes into the side-findings registry with a full description, while the task's report keeps a list of «ID · priority · one
line · status» with a link to the registry. That keeps the verdict on the task from mixing with the quality of the product around it. A
finding **already filed in the tracker** does not go into the table — it goes into an «outside the table» line below it: what reproduces,
the date, a link to the existing task (the ID is consumed in the process and is not reused). A related one (the same root cause, a new
trigger) stays in the table, stating explicitly that the existing fix does not cover it and what should be added to that task's DoD. A layer-labelled task whose other layer's surface is missing («the feature is not visible in the UI» on a backend task) is sorted by «A requirement whose SURFACE is missing», above.

## Setting the priority

**The second question after «what is broken» is «will the user see it today».** A defect observable only through the API — the screen that would show it does not exist yet, and no live task carries it (where one does, the row is a line under the table, «A requirement whose SURFACE is missing») — is a `Minor` with the deferred risk named, not a `Major` in advance; the customer's first question about such a row is «what is the risk?», and a priority that cannot answer it gets lowered and the cell rewritten. **Where that rule collides with another calibration on the same finding** («data and audit quality — `Major`»), two questions decide it: can it still be repaired later (a record in an append-only journal cannot be rewritten, so «no screen yet, they will fix it in time» does not hold), and is it a requirements gap, which the scale rates `Major` whether or not a screen exists. Write the choice and its reasoning into the cell, so the customer argues with the reasoning, not with the label. Precedent: two generations of a role name in a write-once journal whose field no screen displayed — the irreversibility, not the visibility, set the priority.

**The severity of a security finding is reconciled with the standard or the widespread practice BEFORE it is written — «sounds serious» is not a calibration.** For authentication and cryptography the anchor is the governing RFC or the reference implementation, not the first impression: ask whether the behaviour is a common, documented relaxation and what the attacker must already hold to exploit it. Precedent: a one-time code accepted twice within its validity window went in as `Major`; the TOTP RFC showed it to be a widespread relaxation, exploitable only after an interception that has already happened — a `Minor`.

**A finding of the shape «the protection is bypassed / access was gained» is proven by a FULL and SYMMETRIC before/after measurement over SEVERAL representative operations — before the conclusion is written.** Whatever the cell will claim («full access»), measure the same set in the protected state and after the bypass: a profile read, a data read, the ability to mutate. The set measured «after» must contain the set measured «before»; three endpoints before and one after, extrapolated into «full access», is a claim the round does not hold. Precedent: after a second-factor bypass only the profile read was measured, the conclusion spoke of full access, the customer asked for proof of the other two — and the whole scenario, logins and factor setup included, had to be replayed.

## Wording a finding

### The first bold sentence

**The opening sentence of a finding is the most-read line of the report and the one most often wrong — four disciplines govern it, and each was paid for by a finding the customer sent back.** It answers one question, in the requirement's own words, and every noun in it is either visible in the interface or present verbatim in the evidence.

- **Compressing into a business phrase has no right to make the finding literally false.** «Missing / not shown» is written **only if the element does not exist at all**; it exists but not in that block, not in that form, not at that level of detail — the phrasing must preserve that («shown only broken down by organizations», «present in a tab rather than in the main information»). The test before delivery: the customer reads the phrase, opens the screen — will they see a direct contradiction? Precedent: an exact «there is no global role, the per-organization ones are shown and correct» was compressed into «the role is not shown on the card» and filed as a Major — the customer opened the screen, saw the column, and the finding was withdrawn with its id burned.

- **The plain verdict goes first; the explanation is the second sentence, never the first.** A round that digs up a real cause — a closed neighbouring task requiring the opposite, a deliberate scope cut, a contradiction between two specs — produces a better finding and a strong pull to lead with it. The customer's question is simpler and comes first: **was the thing I asked for done, or not?** Lead with the cause and they read a paragraph of analysis before the answer, then ask for it anyway, sometimes twice. So: the first sentence states whether the requirement is met, the cause follows explicitly marked as an explanation rather than a mitigation — and the same ordering governs the verdict block at the top of the report and the tracker comment. Where the requirement has several halves, say plainly that none of them is met instead of leaving the reader to assemble that from the per-half verdicts. Precedent: a round found that the behaviour it was sent to retest was the verbatim implementation of a closed task's acceptance criterion and led with that conflict; the customer needed two follow-up questions to arrive at «so the instruction was simply not implemented at all», which had been true and measured all along. And the verdict names the broken MECHANISM, not only its outcome: «no new client can be admitted to operations» is the consequence the reader weighs, «automatic screening does not start when a company is activated» is what they act on — the mechanism leads in business words, the consequence follows in the same sentence, endpoints stay in the technical line.

- **Frame it in the terms of the REQUIREMENT, not of the surface where you noticed it.** A requirement about a contract (a schema, an enum, a mapping between two systems) yields a finding about the contract; the screen where it became visible is evidence for the technical line, not the frame — and the contract answer is usually both sharper and more damning. The check before writing the cell: re-read what the task is about, then ask whether your first sentence answers *its* question or merely «what I saw». Precedent: the task asked whether the identity provider's role dictionary matches the API's enum; the finding was written about a column caption, and the customer had to send the round back to the API twice — where it turned out that the admin organization contains **zero** holders of the very role name that gates eight of the eleven write operations.

- **Two things smuggle an unverified claim in: a word borrowed from the spec, and a quantifier.** The vocabulary of the requirements and of the knowledge base feels authoritative, but a term the product's own screens never use brings its whole model with it, including structure nobody verified; a spec-only term belongs in the technical line, attributed to its source. Check the quantifier against the evidence the same way — «all five» versus «three of the five» is the difference between a claim and a fact. Precedent: an exact executor finding («all five members of the admin organization are shown as `operator`») was compressed into «the platform owner is labelled an ordinary operator — and so are all five superadmins»: «superadmin» came from the spec and appears on no screen, «the owner» implied a hierarchy the evidence contradicted, and write actions were on record for three of the five. The defect survived, but the customer's first question was about the wording and every derived artifact had to be rewritten.

**A finding about appearance is obliged to name the conditions of observation — window width, zoom, locale, theme.** A measurement taken in
one window describes that window, not the product: clipping, wrapping, overlaps and hidden controls almost always depend on width. Require
(and check yourself) at least two points — a typical working width and a narrow one — and put in the cell the threshold at which the defect
appears. Without that the priority is inflated by an order of magnitude: a narrow-window edge case looks like a permanently broken screen.
Precedent: «the card's title is clipped in half, the full value is nowhere to be found» was taken in a 1190 px window and filed as a Major;
at 1366–1920 px the value is fully visible and the defect lives only below ~1300 px — after the measurements the finding became a Minor with
the threshold stated.

**A defect of the kind «the wrong HTTP code arrived» is filed only together with proof that the right code does reach the client.** Find on
the same host any request that returns the expected code (in one session — a `403` from a public endpoint without the whitelist header) and
quote it in the finding: without that the developer's first move is to write the discrepancy off to a proxy, a WAF or a gateway, and the
round goes into correspondence. While you are at it, check whether the code is visible in the logs: often the middleware records only the
request, and the refusal code is captured solely on the client side.

**A finding whose whole evidence is a NUMERIC CODE — a type id, a status id, a reason code, an error number — is not finished until you have named the dictionary you decoded it with and shown that the dictionary is the product's own.** The failure is quiet and feels like diligence: the executor finds a number in a payload or a log, looks it up in the nearest enumeration they have — the test framework's, a neighbouring service's, one from the documentation of an adjacent feature — and reports the decoded meaning as the observation. Nothing in the evidence marks the substitution, so the finding reads as a direct reading of the system, and reviewers check the number against the same wrong table and agree.

The cheap proof is behavioural and needs no source access: find calls the system makes **on behalf of a different actor or in a different state**, read the same field there, and see whether the numbers line up with the meaning you assumed. Actor-typed fields are the easiest — operations only one kind of participant can perform will carry that participant's code, and one identifier cross-checked against a registry settles it outright. If the numbers contradict your table, the dictionary is not the product's and the finding dissolves; if they match, you have just turned an assumption into evidence at the cost of one read.

Two riders. Such a claim is almost always a **cancellation of a published fact or a confirmation of one** — the number has usually been decoded before, the same way, and the prior reading is what makes the new one feel safe; the rule about re-verifying cancellations yourself applies here in full. And when the finding dissolves, say so explicitly rather than quietly dropping it: the withdrawal has to reach the artifacts that carried the old reading, or the next round decodes the number identically and files it again. Precedent: a finding rated Major said the audit trail attributed an administrator's action to a different class of user, on the strength of a type id read through the test framework's enumeration, where that value meant that other class. Three hours of the system's own journal showed operations only the other class can perform carrying a different number entirely, and identifiers from those rows checked out against the registry of that class — the product's numbering was the reverse of the framework's, the audit was correct, and the same misreading had been sitting in the case notes as a known problem for four months.

**Every finding gets a title line, shaped `Area \ what happens, under what condition`.** The title is what a tracker search matches, so it
is the dedup key for the reconcile rule above: a title naming only what broke, without the where and the when, is the one that gets filed
twice. One line, ~90 characters; **the observable behaviour, not the cause and never «X does not work»**; numbers, ids and selectors in the
body; **one defect per title**, since a chained title gets the task closed on its first item; re-read it after the body is written. Follow
the tracker's own title convention where it has one. Precedent: a Critical went out with a 144-character title chaining three defects, while
its tracker had used `Area \ symptom under condition` all along — neither the finding nor its duplicates were findable by title.

## What «not covered» is allowed to claim

**«Not covered — no access to X» is a claim about a fact, and a claim about a fact is verified by trying.** The profile, a past session's report and the registry all carry such lines and they read as settled infrastructure: no logs, no orchestrator, no console. They are somebody's earlier assumption, sometimes never tested once, and an environment gains surfaces between rounds. Before the row goes in, spend the one call: open the host, send the request, look at the status — and a retest re-tests the access before reusing an old report's reason. **Two things the answer may not be:** a refusal seen in the browser is not proof when the host neighbours one you hold a session for — a stale cookie for the parent domain makes a proxy answer `403` on a host that is in fact open, and a plain `curl` without cookies tells them apart; and where the direct observation genuinely is unavailable, **a surrogate oracle earns its row only together with the line saying what it cannot show** — measuring a process through the artifacts it leaves sees only the runs that produced something, and that shape, written next to the verdict, is what keeps a gap in the data from being published as a gap in the product. Precedents: four acceptance items were written off as «the orchestrator is unreachable», inherited from the project profile — the host answered on the first request and every item turned out to be directly observable; an orchestrator UI answered `Forbidden` in the browser and `200` to the same URL without cookies, and the browser's answer had been taken as confirmation that QA had no access at all; a surrogate oracle showed no activity on four consecutive days, and the caveat line was what stopped «the schedule skipped those days» from reaching the tracker — direct observation later showed the runs had happened and simply found nothing. **And «the channel does not exist» is asked of EVERY contour, because visibility is scoped per identity, not per environment.** The shape: a listing answers `200` with an empty array under the credentials the round happens to hold, which reads as «there is nothing here» — while the same objects are plainly visible through a neighbouring contour, because they were registered by another key, another tenant or another role, and each key sees only its own. An empty list is a fact about the identity that asked, never about the product; the give-away is that the round holds two ways in (a machine API and a human one, an integrator's key and an operator's session) and consulted one. So before the row is written, put the same question to every contour the session can reach, and where they disagree, the disagreement is itself the finding — usually a scoping defect the owner of neither contour has noticed. Precedent: a round recorded «no delivery channel is configured on this environment» from an empty listing under an integrator's key; the operator's contour showed two active subscriptions of that same tenant, one of which had accepted four deliveries produced by the round's own actions an hour earlier.

**A conclusion of the form «X is broken», reached by an unsuccessful SEARCH, is a protocol of the attempt — never a property of X — and it must not enter the profile or the knowledge base in the second form.** The round tries every variant it can think of, all of them fail, and the honest-looking summary writes itself: the credential does not work, the endpoint does not exist, the mechanism is absent. What was actually established is narrower — none of *these* variants worked — and the gap between the two is one parameter nobody enumerated: a header name, a flag, a prefix, an encoding. The damage is not in the report, where the evidence sits next to the claim; it is in the durable artifacts. A line in the project profile or the knowledge base is read cold by the next round as settled infrastructure, and it will stop that round from trying the one thing that works. So write such a finding as what it is — «not reproduced under these conditions, the missing parameter is unknown, here is what was tried» — and keep the verdict «X is broken» for the case where the mechanism itself answered. Precedent: a round could not make a supplied signing secret validate anything and recorded «the secret does not work, treat it as broken» in the report, the profile and the knowledge base; the secret was fine, the round had simply never tried the right header name, and the next round's executor said plainly that trusting the profile over the brief would have cost that round too. **A verdict of impossibility needs proof of impossibility, not a report of failure** — so name the boundary («not verified under conditions X») and offer the user the one action that separates «we could not» from «it cannot», since they often hold the lever. Precedent: «signing through an alternative wallet does not work» collapsed when the user switched the wallet's network and ran two operations in a row.

**A requirement addressed to a component that does not exist is a FAIL of the requirement, not an item the round could not cover — and the difference is the whole verdict.** The shape is quiet and it flatters the round: the requirement describes behaviour of a consumer, a handler, a subscriber («such an event is ignored and logged», «the receiver retries», «the worker skips it»), the round goes looking for that behaviour, finds no channel through which it could ever be observed, and writes «not covered — unobservable by construction». Every word of that is true and it hands the reader the wrong sentence: nothing was measured because nothing was built. Ask, of every «unobservable» row, whether the thing that would do the observing is part of the product's own scope (the full order — «A requirement whose SURFACE is missing», above) — and where it is, the row becomes a defect with a priority, usually carrying the neighbouring requirements down with it, since one absent consumer typically fails a whole family at once. Two riders. Say plainly what DOES work instead, because the business outcome is often delivered by an adjacent mechanism and the reader must not conclude the feature is dead. And check whether the absence was ever ruled acceptable: on a sibling requirement the same channel may have been descoped explicitly, in which case the verdict is «absent, and here is the decision that permits it» — while silence on this one makes it an analyst's question with a finding attached. Precedent: a round reported an acceptance criterion as «not covered, the platform cannot process such messages» on a task whose own title named that very operation; the customer asked how those two sentences fit together, and the honest answer — the consumer of that channel does not exist on the platform at all, four requirements fail together, and the neighbouring task had descoped the same channel while this one never did — was the report's headline, reached only because the customer pushed back.

**«The design has no such screen» is true only of the canvas you actually opened — and a frontend round that made no design comparison says so under «not covered».** A frontend verdict has three sources of truth — the requirements, the attribute tables, the design — and they disagree; the UI is compared with all three and a disagreement is recorded with every variant, the analyst choosing the canon. When the design was not opened at all, the report must say so, or the reader assumes the UI was reconciled. Where it was opened through a design tool's MCP, two limits shape the claim: a live node's metadata runs to hundreds of kilobytes (read the file the tool saved and parse it with a script, not the reply), and the file's canvases may not be listable at all — so only the canvas behind the link you hold was checked, and «absent from the design» is written as «absent from the linked canvas». Precedent: a linked canvas held six screens and none of them the dashboard the sidebar drew a link to; the tool listed a single empty navigation page for the whole file, so nothing could be said about the rest of it.

The planning-time half of this rule — the cheap move that closes each shape before the plan records it — is in `planning.md`, «Before a requirement is planned as "not covered"».

## The table's own mechanics

**The findings table is written to be copied out whole, into a tracker, and read by a developer who has neither the session, nor the files, nor the history of the runs.** Everything below follows from that one fact, and the first two are checked mechanically before delivery — the checker at step 6 verifies the bar count, the cell length and stray secrets in one pass.

- **A vertical bar inside a cell breaks the table silently.** Enumerations («the columns `ID | Name | Status`»), regexes and logical «or»s are read by markdown as column separators: the row falls apart, and the one who sees it is the reader. Inside cells, enumerate with commas or `·`. Check that every row carries the same number of `|` as the separator row and that no cell exceeds the length limit — a cell written to feel «short enough» comes out at 900–1000 characters about as often as not, and the customer sends the report back to be trimmed. Precedent: the customer saw broken layout in a delivered report.

- **HTML inside a cell renders in your editor and breaks in the tracker.** A `<br>` looks like the obvious way to fit a second tier of information into one cell, and markdown previews it correctly, so nothing signals the problem while the report is being written — while the destination renders a restricted markdown that prints the tag as literal text. The rule is flat: **no HTML in the findings table, `<br>` included.** A second tier goes below the table as a compact list keyed by the finding's id; where it is not needed, the cell is one flowing paragraph in the order the format prescribes. Precedent: nine `<br>`s went out in a delivered report and the user caught them — no past report of that project contained a single HTML tag, so the layout had been invented by the manager rather than taken from the project's format.

- **What stays out of the cells:** anything fixed (it moves to a block below the table and into «Round history», never a row with a status), paths into the QA repository of any kind (the session, the registries, the knowledge base, the executors' results — in the tracker such a link leads nowhere: write the fact itself, what was measured, with what, when and on which build, or the id of a tracker task), ids of your own from other runs («pattern B3/B5», «family F7/F13»), and internal designations (round numbers, plan items) — those become words and a date. Ids of tracker tasks, environment entities, endpoints and activities are needed, and cross-references to your own findings and files go in the text below the table.

- **Splitting by LAYER is not discharged by grouping by theme, and it happens before the ids are assigned.** A thematic grouping reads well and is worth doing; what it cannot do is answer «who fixes this», which is the first question the table is read for — the layer is the address, the theme is the order inside it. Where the ids encode the layer, splitting after they are handed out forces a reissue: the finding moves to the other prefix, the old number is burned for good, and every artifact already carrying it needs a note. Sort by the defect's nature inside each layer. **One id or two is decided by what each half IS.** A single defect whose fix needs both sides (a server keepalive plus a client re-read) keeps one id, by its nature, and the second half is named in the prose below. A finding that measurement splits into two defects — each with its own symptom, observable and fixable on its own layer — becomes two ids, one per layer: the existing id stays with its own half (neither relabelled to the other prefix nor burned) and the other half takes the next number, because a developer cannot fix the other layer's half under their own ticket. A project's profile may set its own numbering convention; where it does, it wins. Precedent: a report delivered with a good thematic grouping was sent back for the layer split, and the split immediately exposed a UI defect filed under the backend prefix — one id burned and reissued, purely because the split came after the numbering. One layer rule that is easy to get backwards: where the defect's sign is already in the API response (a machine-readable error) and the client does not handle it, the finding is the frontend's; a wish to the backend goes as a second line, not a blocker.

- **On a long-lived registry session, «is this already filed in the tracker» applies to the INHERITED rows too, every round.** That rule reads as being about classification, so it gets applied to new findings; an inherited row is not classified but *updated* — re-measured, marked «still reproduces», reworded — and never asked the question again. A row can acquire a task between rounds, and on a session running for months it usually does: somebody files the defect from a neighbouring session, the analyst converts it during grooming. The table then publishes as open something the team has already accepted and scheduled, and the customer who knows the task exists reads the whole table with less trust. So for every row carried over, search the tracker before touching its wording, and where a task turns up, move the row out with its date, the link and whatever this round added — the measurement is not wasted by the move, since confirming that a scheduled defect still reproduces is exactly what the owning task needs. Precedent: a row had sat in a registry table since the round that opened it two months earlier; a task had been filed in the interim, the retest updated the row's wording in place, and the customer asked why a finding with its own task was still in the findings table.

- **«Filed in the tracker» is claimed only when the finding's OWN identifier (or its unmistakable text) appears in a task — a task whose scope merely covers the area is «related», never «filed».** The two read the same in a busy cell, and the difference decides what the customer does next: «filed» tells them to stop, «related» tells them a task exists that may or may not carry this defect. The inference is tempting because the round usually found the finding *through* that task — a retest of a registry, a requirement read from an epic — so the manager writes the task's number next to the finding as its home. Check it the cheap way: export every task of the project with its description once and search it for the finding's id with a word-boundary regex; a hit is «filed», a topical match is «related», nothing is «not in the tracker». The same export also answers which of the round's *known* confirmations were filed by the customer from earlier reports. Precedent: a finding went out marked «filed in» the registry task through whose retest it had been found; the export showed its id in no task at all, and the column had to be corrected for it alone.

- **A finding whose status changed MOVES between sections — it is never re-labelled in place.** The move runs both ways: a fixed finding that breaks again returns from «Fixed» to the table under its own id, the cell opening with «regression R<n>, <date>» — a fresh id would split one defect's history in two. Appending «— fixed» to a row costs one edit and leaves the row under a heading that still says «open», beside a per-section count that still includes it; the heading, the counts, the summary line and whatever the chat message says are all derived from membership, and an in-place edit updates none of them. The move is the cheap operation precisely because it forces the rest: cut the row, paste it under the section its new status names, then recount the headings and reconcile the totals with the summary before anything is delivered. The pull toward editing in place is strongest late in a session, when the structural version of the same edit was already done correctly an hour earlier for other rows — the manager knows the right shape and still reaches for the smaller diff. Precedent: two findings closed by a retest were updated by rewriting their cells; the section heading above them still read «open findings», the counts still said three and four, and the delivery message claimed five open while the file held seven — the customer caught it. **And the requirement rows that CITE the finding are re-verdicted in the same pass.** The move above relocates the finding; the verdict table keeps a separate row per requirement, and one of those rows usually explains its `partial` by naming the finding («the list still shows a zero — F-7»). Closing the finding leaves that row asserting `partial` for a reason that no longer exists, a few sections above the block announcing the closure, and the totals line inherits the error. That table is what the customer reads for progress, so the contradiction lands in the most-read part of the document and survives every later round, because nobody re-derives a verdict that already has one. Grep the verdict table for the finding's id whenever its status changes, re-verdict every row that names it, and recount the totals. Precedent: a row stood at `partial` citing a finding that had been closed and re-verified four days earlier; the report's own closed-findings block contradicted it in plain text, and the published pass count was one short for two rounds.

- **On a retest, every verdict row is transcribed from the EXECUTOR's own table — never re-derived from the previous round's report.** The old report is the richer document: it is already in context, its rows carry their reasoning, and its wording is the manager's own. So the rows that changed dramatically get rewritten with care, while a row that merely *shifted* — partial to partial for a different reason, or pass to partial because this round finally compared against the full attribute list — is carried across in its old framing and published with a verdict the round never passed. It reads as a small slip and it is the load-bearing part of the document: the customer's entire picture of progress is that column. Copy the verdicts mechanically, then reconcile the totals against the executor's own count — a disagreement in the totals is the cheapest detector there is. Precedent: two rows went into a delivered report as «pass in substance» while the run's own table said partial, and the error surfaced only while the delivery's status list was being assembled from the counts.

- **Requirement identifiers that exist only inside the round may not be used as references in the report.** Where the source has no numbering — a task written as prose, a comment thread, a mock-up — the round still needs handles for its requirements, and the natural move is to number them (`FR1…FR8`) in the plan, then carry those labels into the report's verdicts, its «not covered» rows and its findings column. Inside the session's own files that is fine and useful. In the report it is a private code: the reader opens the tracker, searches for `FR2`, finds nothing, and has to ask what it refers to — and every sentence built on it becomes unreadable at once, because the labels are exactly where the verdicts live. Two ways out, and either is acceptable as long as the report is self-contained: publish the mapping (a short table «label → verbatim quote of the requirement») before the first verdict that uses it, or drop the numbers and name each requirement in words, quoting the source fragment. Prefer the second where the source is unnumbered, since an invented number also implies a structure the requirements do not have. Real numbering — an `AC-3` that exists in the spec — is quoted as is and needs none of this. Precedent: a report's verdict list and «not covered» table were written entirely in `FR1…FR8`, invented by the manager; the customer's first question after delivery was «what is FR-2? — either publish which numbers you assigned, or reference the text».

- **A finding about TEXT THE USER SEES is published only with a screenshot or the string quoted from the served bundle — and a disagreement between the two is a reason to re-measure, not to pick one.** Labels, statuses, button captions and error strings are the cheapest findings to file and the easiest to get wrong: the same status may be rendered by a different component elsewhere, or the build may have changed under the executor. The served bundle settles it independently — its localisation map is the product's own answer to «what should this say» — and grepping it costs one request. When screen and bundle disagree, neither is automatically right: the bundle may describe a component nobody opened, the executor may have been on a stale build. Publish the finding with the disagreement named and the one observation that would settle it. Precedent: a finding said a rejected request is labelled with the wrong word; acceptance found the localisation map using exactly the word the spec demands, could not re-render the screen, and published the finding flagged as needing a single observation — which is honest, whereas both withdrawing and confirming it would have been a guess.
