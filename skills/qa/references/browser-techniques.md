# Browser techniques

Read by `qa-manual` on any round that drives a browser or scripts a page — the first screen and the sections the brief names before the
first page script, any other section when you reach its topic — and by the manager before the preflight at step 4 of `../SKILL.md`: the
first screen and the contents, which is how the brief's sections get picked. The recipes hold for any page-driving tool and in any project; the limits and failures of ONE tool — its call budget, its output filter, how it picks a tab — are in `browser/<tool>.md`, named by the profile's `browser`, read beside this file; what
belongs to one project — its hosts, its entry, its own UI quirks — stays in the profile's Browser section, which is read after this file and
wins where the two differ. Requests to the API itself — the contract, the replay, reading the answer, GraphQL — are in `api-techniques.md`, which a
browser round reads beside this file. Every recipe below was paid for by a lost round.

## TL;DR — the typical flow

1. **Navigate to the target screen first, then install helpers and interceptors** — `window.*` dies on `navigate`/reload (it survives SPA transitions).
2. **Read the entity's state through the API before looking for it on screen** — a user or a process may have moved it since.
3. **Print derived values, never raw bodies, markup, source or access** — and around the tool's own output filter, where it has one (its adapter).
4. **One page-script call stays under the tool's budget** (its adapter); longer work accumulates in `window.__…` and is read by a separate short call.
5. **Headless-component controls**: native `click()`, a pointer sequence, `focus()` or a real click by coordinates; verify by the state attribute, never by «Clicked».
6. **The tab is hidden and throttled**: force a render (a screenshot) before any verdict about a control, and wait with `MessageChannel`, not `setTimeout`.

Pitfalls and the full recipes, by topic, below.

## The page-scripting sandbox and its limits

- **Every page-script tool caps one call — the cap is in `browser/<tool>.md`, «Page scripts and their budget» — and everything inside it adds up**: a wait plus the fetches after it count together. Wait for a boundary (the next TOTP step, a timer) in its own short call, never in the call that does the useful requests; where a loop may overrun, push every sample into `window.__acc` and read it with a separate call — a timed-out call loses its return value, not the accumulator. **A wait inside a call is on the EVENT where there is one (a single `MutationObserver` or listener), and on the `MessageChannel` loop from «The hidden tab» where time itself has to pass** — never a loop of timer sleeps, which the hidden tab throttles.
- **A call that timed out has usually still run** — its fetches went out and the script keeps executing in the page. Re-read the state with a separate request before doing anything; never re-run a timed-out call that installs a substitution or a wrapper, or a second one lands on top of the first.
- **A native `alert`/`confirm`/`prompt` freezes the page for the tool** — every later script and screenshot hangs until a human dismisses it. Do not trigger them; where a flow ends in one, stub `window.confirm` from a script before the click and record that you did.
- **A reference dataset needed across navigations lives in `localStorage`, not in `window.*`** — a full export of a registry survives every transition between the list and the cards without a single re-export. Name the key with a prefix unique to THIS run (`__qa<task>_<round>_…`), and in hygiene remove the exact list of keys you created — never everything under a shared prefix — then confirm by reading back `null`. The origin's storage is shared by every session that ever worked on the environment, and earlier rounds leave keys there on purpose. And a value a result file relies on is written INTO the result file: storage carries data between navigations, it is not where evidence lives. Precedent: a cleanup filtered by `startsWith('__qa')` deleted 26 keys left by two earlier sessions, one of them the only copy of a snapshot a published result cited.
- **`window.*` survives an SPA transition and dies on `navigate`/reload** — helpers, loggers, a saved original `fetch`. So: navigate first, install after; save the original once (`window.__origFetch = window.__origFetch || window.fetch`, or you wrap the wrapper); before any conclusion check the wrapper is still live (`window.fetch !== window.__origFetch`); restore it when done. The tool cannot read files, so keep a long wrapper as a file in the scratchpad and paste it verbatim after every navigation — a reload by the user or by a silent session renewal kills it as surely as your own `navigate`.
- **A browser extension injects into a document only when it loads.** After an extension is switched on or off, the open tab keeps the old world — no injected globals, no announcement events — until it is reloaded; prove the new state with your own probe after the reload, never from the user's word that it is switched. So «the capability appeared while the page was open» is never planned as a person flipping the switch on the extensions page: the open document gets no event and the pause buys nothing — use a provider announced from the page itself, or a real install before load.
- **A session is observed without the application by opening a non-HTML static file of the same origin** (an SVG icon, an image): page scripts run there, `location.origin` is kept and a credentialed `fetch` carries the cookie, while the SPA that would renew the session in the background never boots. A deep route or `robots.txt` will not do — the catch-all serves the index document and the application starts.
- **Arm an observer in the SAME call as the action that produces the event** (see `manual-brief.md`, «The observation channel»); the first entry of a «record only changes» accumulator is always written and is not the moment of a transition.
- **A full id is never reconstructed from a truncated one.** Tables and your own `slice(0, 8)` summaries show ids cut short; a tail
  «remembered» into a UUID answers `not found` and burns the call. Put full ids into `window.__ids` (or `localStorage`, if a navigation lies
  ahead) at the moment the list query returns them, and print only the short form **to the console** — the result file still gets every id whole (`qa-manual`'s rule): print it character by character (`.split('').join(' ')`) where the filter cuts it, or fetch it from the shell.
- **Mocked amounts are strings, never arithmetic** — `String(i) + '000000000000000000'`: mixing `BigInt` and `Number` throws at once, and a `Number` loses precision at 18 digits.
- **On macOS there is no PIL — crop and scale with `sips`**: `sips -g pixelWidth -g pixelHeight in.png` first, then `sips -c <h> <w> --cropOffset <top> <left> in.png --out out.png`, `sips -z <h> <w>` to upscale. Without the size a crop misses the region.

## What is printed

- **Print derived values, never raw bodies, markup, function sources or access** — a long raw print costs context in any tool, and in a tool with an output filter (Claude in Chrome: `browser/claude-in-chrome.md`, «Output censorship») it is lost outright. Where the tool cuts or blocks output, its adapter says how to print around it; a value that never came back was not measured.
- **Responses carry access** — presigned storage links, one-time session links sent to a person, tokens, cookies. Never print them; before a text goes into a rendered node, cut them out of it. *And a question about such a link* — «does it still serve the file», «is it the bytes that were uploaded» — is answered INSIDE the tab the link opens, never from the app page: open it through a real click, then run the check in that tab, whose origin is the storage host — `fetch(location.href)` there passes no CORS and gives the status, the type and a sha256 to compare with the uploaded file; a second link reaches the same tab by `postMessage`, the listener accepting only data shaped like the expected URL (`startsWith('https://')`) and logging every message, since unrelated messages arrive in a tab around script calls and read as the storage refusing a fresh link. From the app page a `fetch` to the storage host is cut by CORS, and an `<img>` probe answers from the browser cache if the file was shown before. Precedent: a first round settled «served after deletion» by the look of the opened tab and gave up on a status code; the next round got status and sha256 from inside the storage tab, after two false «403»s from an unfiltered message listener.
- **A large captured text (an export, a payload) is compared, not printed**: hash it line by line (sha256, via `crypto.subtle`) in the page and compare against a local copy. **A UI caption is checked against the spec the same way — in code, character by character, printing the positions that differ with their character codes**: look-alike letters (a letter with and without its diacritic, Latin against Cyrillic) are invisible to the eye, and arguing over one costs a round.

## Intercepting, replaying and substituting network

- **A `fetch` wrapper can break the application's own submit** — the form shows a generic «something went wrong» toast while the request actually went out and succeeded (or the submit travels by XHR and the wrapper sees nothing). So the happy path through the UI runs WITHOUT hooks; a hook goes in only where an id or a response body is needed, and then any result obtained under it is suspect until a control run without it. Server-side validation is tested by a separate direct request, not through the hooked form.
- **The request logger keeps every body whole; truncate only when printing.** `JSON.parse` of a truncated string fails with `Unterminated string`, and the capture has to be retaken.
- **A client with a normalised cache answers from the cache, so a substitution installed after `navigate` loses the race.** Load an unrelated route in full, install the interceptor on the empty cache, then move to the target by an SPA transition: `history.pushState({}, '', '/target')` + `dispatchEvent(new PopStateEvent('popstate'))`. A modal whose data is read cache-first takes the substitution only if it is in place BEFORE the modal is first opened.
- **A spy logs the request AND the response, filtered by the page's own operation** (a GraphQL `operationName`, a REST method and path) — a spy on requests alone reports «the upload silently fails» while the server answered `success: false` with a reason, and a substring filter mixes your own control queries into the page's log. A tool's own network log is no substitute (its limits: `browser/<tool>.md`, «Network»): «which variables went out», «what the server answered» and any race or timing question («were these in flight together») need your own spy stamping `Date.now()` on each entry. Toasts render at the end of the DOM: look for them in the tail of `body.innerText`, never in its first N characters.
- **One install serves a whole family of variants when the mock answers for fictitious ids** (`qa-01…qa-NN`): the cache is keyed by variables, so every new id is a guaranteed trip to the network and a fresh mock — `pushState` to each in turn. The same install renders every status of a dictionary plus one deliberately unknown value in one pass: the mappings and the fallback at once. **The fictitious ids reach the NESTED entities too** — the author of an event, the wallet, the organisation: a normalised cache merges every object of a type by its id, so a mocked author sharing an id with a real user (or with another object in the same response) is merged with it, the last write wins, and the screen shows a field you never sent. It reads as «the value does not render even when filled» — exactly the defect under test, produced by the harness. Give each nested object its own fictitious id (`qa-actor-0001`), and when a mock renders something unexpected, read the cache entry (`cache.extract()['Type:<id>']`; reaching the cache — `api-techniques.md`, «The client's cache») before reading the screen. Precedent: a control for «an event author with an empty name is invisible» first came back invisible WITH the name filled — the mocked author shared the initiator's real id, the cache kept the empty name, and two substitutions were spent before unique ids gave the clean pair.

  *And where the mock BUILDS rows from a real one* (a list padded past its real total to reach a second page): keep the template from the
  first non-empty response — the server answers a page beyond the real total with an empty list, rows built from that come out without
  fields, and the page throws a `TypeError` that is the harness's, not the product's (re-installing a network route: `browser/<tool>.md`,
  «Network»). Precedent: a substituted pagination crashed the page twice on the second page before the template was frozen.
- **Patch the response by the SET OF FIELDS, not by a guessed path.** The root field of the application's own operation often differs from the one in your hand-written query, and a patch aimed at the wrong path silently returns the untouched data — no error, a real screen, a substitution counter of zero. Walk the JSON recursively and rewrite every object carrying the fields you target (`status` + `failureCode`, say); diagnose a miss with `Object.keys(j.data)`. **Where the state to fake is an ABSENT object — a field that comes back `null` — a field-rewriting walk finds nothing to rewrite and succeeds silently:** substitute the whole object in place of the `null`, built from the type's own selection set in the application's query, and learn which operations carry that field from an interceptor first, since the client often reads it through more than one. Precedent: a gate that opens on «a limit exists» was to be reached on an entity with no limit record at all; the previous round's walk, which rewrote an existing limit's value, would have left every response untouched.
- **To prove «what was confirmed is what was sent», substitute the computation with values nobody else would produce** — comparing equal numbers proves nothing when the server computes the same figures itself. Choose values valid for the domain, or the experiment is smeared by a validation error.
- **An irreversible mutation whose CLIENT reaction must be seen goes through a fail-closed `fetch` wrapper.** Installed after navigation; it blocks every request that performs the operation (GraphQL: parse the `query` for the mutation field — the operation name can also travel in `variables`; REST: the method and the path); substitution is armed by hand for one request and disarmed after it; not armed, or an unparseable body → a stub response such as `QA-BLOCKED`, never a pass-through. Before the first click, self-test it with a direct call and prove the application goes through it (an SPA transition, then the application's request in the log). Build the substituted body from the intercepted response's own shape (for GraphQL, the query's selection set); after each run, count the entities through the saved original `fetch`. The wrapper is removed right after the last click it guards, not at the round's end (the browser's case of the «Disarm after» rule, `manual-brief.md`): a tab that drops out of the tool's group keeps it in blocking mode, and later actions in that tab — the user's own included — are refused with nobody watching. **The same wrapper is the oracle for CLIENT-side validation**: a blocked mutation that logs its payload answers both «did the invalid input send a request at all» and «which values did the form put into it» (a field stuck at a previous value shows up there, not on screen).
- **A race the real network is too fast to produce (a stale response landing after a newer one) is made deterministic by the spy's `fetch` wrapper delaying ONE response**, selected by operation and variables, with the delay written next to the verdict — a pass under it is a pass, a defect under it is stated with the delay that provoked it.
- **Substituting persisted state does not reach the copy the application already holds in memory.** Rewriting an expiry or a flag in `localStorage` leaves a hook that read it at mount working on the old value; the background tick arrives on its own schedule. Such a substitution is at most an accelerator with an explicit «did it take» control — a verdict resting on it rests on a coincidence; the verdict comes from waiting for the real tick.
- **A WebSocket logger is a patch of the PROTOTYPE** — `WebSocket.prototype.send`, `.addEventListener` and the `onmessage` setter. Client libraries capture the constructor at bundle init, so a wrapper over `window.WebSocket` installed after load stays empty while the subscription works.
- **Neighbouring screens are read in a second tab** while the first holds a live subscription or observer — an SPA transition away closes the subscription in the most interesting window.

## Component-library interaction

- **Clicks by an accessibility `ref` inside modals, dropdowns and tabs of headless libraries (Radix and the like) often do nothing, while the tool reports «Clicked».** Order of attempts: a native `element.click()` from a page script (buttons, menu items), then coordinates from a fresh screenshot; pick options with `querySelector('[role="option"]')` + `click()`. Verify the result, never the intent — a state attribute or a screenshot after every step.
- **Tabs (`[role="tab"]`) ignore a native `click()`, and which substitute works changes with the library's build.** Order of attempts, each controlled by reading `data-state` before and after: dispatch `pointerdown → mousedown → pointerup → mouseup` with `{bubbles: true, cancelable: true, pointerId: 1, isPrimary: true}`, then `click()`; where that leaves the tab `inactive`, `element.focus()` — tabs in automatic-activation mode switch on focus (not reliably: seen working in one of two attempts); then a real click by coordinates from a fresh screenshot. A recipe that worked in a previous round is a first attempt, not a guarantee. Precedent: the pointer sequence a case prescribed stopped switching tabs after a frontend redeploy; `focus()` and a real click did.
- **A tooltip on a disabled control opens on `pointerenter`/`pointermove` dispatched on its wrapper** — the tool's hover misses a covered target.
- **Opening a dropdown or a side drawer shifts the layout** (a drawer can even change the frame size — «The hidden tab», viewport): the «fresh screenshot» for picking an option or a field is the one taken AFTER that dropdown or drawer opened; check the selected value before submitting.
- **Any change of markup voids remembered coordinates** — a changed select, a reopened modal (forms often keep their error block after «Cancel», shifting every field). Re-take `find` or a screenshot and click the fresh target. **Any navigation or reload voids every `ref` taken before it** — a click on a dead ref still reports «Clicked on element» and lands nowhere, with no sign of invalidity.
- **A disabled control often has no handler at all** — removing `disabled` achieves nothing; check the handler's presence (`memoizedProps.onClick` on the React fiber) before building on it, and prefer substituting the READ so the application enables the control itself.
- **Refilling a form after a transition is checked field by field against the previous captured request body** — a checklist, not memory; an optional field is the one that silently drops.
- **A drawer or modal form can keep its values between openings** — until another record is opened or the page reloads, so the next scenario measures what the previous one left. Reload between form scenarios, and before «the wrong value was filled in» rule out your own earlier draft.
- **Setting an input's value from a script does not revalidate a form library's state** — the native setter plus an `input` event changes the DOM value, while the message under the field and the submit's `disabled` stay from the previous value (react-hook-form: two false boundary measurements in one round). Validation of a TEXT field is measured by real typing only; a scripted fill is at most preparation, controlled by a second, typed entry. And the typing tool is not exact on long strings — 301 typed characters arrived as 297 and as 302 — so a length boundary is reached by a scripted fill to one below the limit plus the last characters typed, and the field's `value.length` is read back before the message under it is believed. A file field cannot be typed into, and its limits are measured by substitution (below), read off the rendered chip.
- **Copy-to-clipboard buttons inside table cells swallow row clicks** — the value goes to the clipboard, no navigation happens, and it looks like «the row is not clickable». Aim at a cell without a control.
- **`textContent` holds text the screen clips** — an ellipsis (`text-overflow`) hides the tail while every read returns it whole, so an
  inventory of what the user can read checks `scrollWidth > clientWidth` per item or looks at a screenshot. Precedent: a permission
  list matched by `textContent` hid the clipped words a fix had just added; only a screenshot taken for another reason showed them.
- **A table cell's value is read from the DOM (`tr.cells[N].innerText`), not scrolled into a screenshot** — a wide table loses its horizontal scroll after a reload, a scroll does not always reach the edge column, and one call replaces a series.
- **A modal can take seconds to mount, and a second click closes the one that just opened.** One click, wait (up to ~10 s), then check `document.querySelectorAll('[role=dialog],[role=alertdialog]')`; whether the click reaches the element at all is shown by a capture-phase `click` listener, not by clicking again.
- **An open popover eats the first click outside it, and after a drawer closes the first click on a row menu can vanish too — non-deterministically** (on one page two controls of four needed a second click, two did not). **The same happens to the first click after a page-script call** (three of four in one round, four misses in a row in another) **and to the first click and key press after a modal closes** — focus stays on the removed node, so even Escape does nothing. For a control that sends a request, plan two clicks on a fresh target with a request-log check between them; for one that OPENS a modal or a menu, the rule below wins — one click, then wait and read the DOM, since a second click closes what the first one opened and the log stays empty either way. After a dialog closes, click into the remaining container before pressing a key. Neither a second click nor a working first one proves anything; «the control is dead» is proven only by the request log (`manual-brief.md`, «A finding of the shape «the control does nothing»»).
- **Coordinates from `getBoundingClientRect()` can miss the screenshot's (by ~20 px vertically, seen)** — the click lands beside the target and reads as «the button does not work». Take coordinates from a fresh screenshot, not from the DOM.
- **A transient message is proven absent only by a `MutationObserver` armed before the action.** A specific validation text can live 1–4 ms before a generic required-field error overwrites it; polling at 200 ms and reading the page afterwards both miss it, and «no error message» nearly became a finding. Observe the dialog with millisecond timestamps — it yields both the fact and the lifetime.
- **Client-side limits of a file field are measured by substituting a `File` of the needed size into `input[type=file]`** + `dispatchEvent(new Event('change', {bubbles: true}))`, reading the outcome from the rendered chip: every boundary point (0, 1, limit−1, limit, limit+1) without a byte of traffic or an artefact on the environment. The upload tool itself refuses files above ~10 MB, so large fixtures go in this way anyway.

## The hidden tab

- **The automation tab usually runs hidden (`document.visibilityState === 'hidden'`) for the whole round, and that changes what controls appear to do.** `requestAnimationFrame` does not tick, so a closed modal stays in the DOM with `data-state="closed"` and reads as «cannot be closed». A screenshot forces a render: run «click → screenshot → read the DOM» as one batch, and never write «the control does not react» before that sequence.
- **Timers are throttled** — `setTimeout` to ~1 s at once, and after ~10 minutes hidden to about once a minute, so a call that took seconds early in the round hits the call budget later. Wait inside scripts with a `MessageChannel` loop (a promise on `port1.onmessage` after `port2.postMessage`, checked against `performance.now()`), which is not throttled. A latency measured by the page in a hidden tab (a webhook's arrival, the time to a status) is inflated the same way — measure it by the server's own timestamps. A long observation by an in-page `setInterval` sampler that records only changes works while the tab is in front; hidden, its log silently stops growing and reads as «the environment froze» — the sign is a last entry much older than the elapsed time, and in a hidden tab the observation is polled from the tool instead.
- **Tooltip rendering lags one hover behind** — synthetic events and the tool's hover alike show the PREVIOUS hover's tooltip. Trust only the tooltip whose trigger reads an `*-open` state (its `aria-describedby`), or a screenshot after moving the pointer to empty space between hovers. «There is no tooltip» is a verdict only on a freshly loaded page: after many SPA transitions and substitutions hover stops opening tooltips at all.
- **Toast libraries pause their timers while `document.hidden`** (sonner does) — a toast that never disappears is not a defect. Before any verdict about toast lifetime: `Object.defineProperty(document, 'hidden', {get: () => false})`, the same for `visibilityState` → `'visible'`, then `document.dispatchEvent(new Event('visibilitychange'))`. **The feature under test can gate on visibility just the same** — an expiry, a renewal, a poll that runs only while the tab is shown — and in the automation tab, hidden for the whole round, that logic simply never fires: «nothing happened when the code expired» is then the tab, not the product. Grep the served code of the scenario's timer for `visibilityState`/`hidden` before the wait, substitute visibility from the first call when it is there, and say in the result that the observation was taken under the substitution; the real hidden-tab behaviour is worth one line of its own. Precedent: an expiry retest would have closed at five minutes as «the code silently renews, the fix is absent»; the timer ran only in a visible tab and the expired state arrived at minute twenty.
- **Each automation tab has its own emulated viewport, different from the user's window and from the next tab** (`outerWidth` of zero or below `innerWidth` is the sign). Read `innerWidth` as the first call and after every resize — and the frame changes without any resize of yours (three sizes in one round; a side drawer opening flipped it 1372 ↔ 1646 px), so take the size from each screenshot's reply before using its coordinates; in a narrow viewport, `scrollIntoView` a cell before a real click and follow links by a native `a.click()`.
- **After a background change (funds arrived, a status moved) the UI keeps its cached value, and forms validate against it.** Plan the reload as its own step rather than discovering the stale value at the submit button.
- **An expired session does not break the page** — the API already answers `401` while the table keeps showing the previous results, with no error and no empty state. Before any conclusion drawn from data, confirm the identity with one query: «nothing changed after the filter» may be a dead session, not a broken filter. A widget's counter is checked the same way — against the direct query, never on its own (a card widget showed 0 where the list held 334).

## Downloads

- **Chrome blocks repeated automatic downloads from one origin after the first** — later files never appear while the application shows its success toast; that is the browser, not the product. The control costs one call: trigger two downloads of your own from the same page (a `Blob` + `a[download]`); both missing means the browser.
- **Capture the file at the source instead**: intercept `URL.createObjectURL` and `HTMLAnchorElement.prototype.click` — you get exactly the `Blob` the product handed over (`blob.text()`, `size`, `type`, and `a.download` for the file name), which is more precise than the file on disk. A download that did land is read from the shell (`ls -lat ~/Downloads/<mask>`) and copied into the session's artifacts.

## Bundle and route discovery

- **«This string is not in the build» is established across EVERY chunk, not the entry script** — vendor chunks carry texts such as empty states. List the chunks from the page: `performance.getEntriesByType('resource')`.
- **«Where does the frontend take this value from» on a page already rendered is answered by grepping the served bundle, not by a spy** — the network tool records only from its first call and a cached SPA does not re-request on a tab switch. A search by the function or contract-method name shows at once whether the value comes from the API or is computed on the client from its own reads.
- **A dictionary of statuses and captions is taken from the bundle, not guessed from the screen**: `document.querySelectorAll('script[src]')` → fetch each chunk → search for the locale keys and the mapping object beside them. It also yields statuses without a tab of their own and dead strings no screen renders.
- **Table columns are found in the bundle by `header:`, not by `accessorKey`** — a composite column is declared with `id:"…"` and no accessor, and a search by accessor loses it (one reconnaissance counted 8 columns of 9).
- **A route map comes from the string literals `"/…"` in the bundle** (`re.findall(r'"/[a-z][a-z0-9/:_-]{1,40}"', bundle)`), not from `path:"…"` — the minifier leaves only `path:"*"`.
- **A blank white page while the API answers `200` is a stale bundle, not a broken product.** The cached index document references a chunk the deploy removed; the server answers its path with the SPA fallback, and the console shows `SyntaxError: Unexpected token '<'` on `/assets/index-*.js`. Diagnose in order — empty `body.innerText` → console errors → compare the chunk names in a `fetch('/index.html', {cache: 'no-store'})` with the loaded `script[src]` — and cure with a hard reload or a cache-busting `navigate`. Re-take the bundle fingerprint before writing ANY UI finding, not only at the round's edges: a deploy artefact is the cheapest false finding there is. A chunk already replaced on the environment can still be read from the cache of a profile that loaded it before the deploy (`fetch(path, {cache: 'only-if-cached', mode: 'same-origin'})`, recipe in `planning.md`, «Dating the build»).

  *And the stale build can render whole, with no white page at all.* Where the server gives the SPA fallback of deep routes a long cache lifetime while the root is served uncached, a direct `navigate` to a deep route the profile opened before runs the previous build complete — every screen works, only the feature under test is missing, and it reads as «not deployed». So on every screen reached by a direct `navigate`, compare `document.scripts` with the chunk the root serves, and give each direct navigation a cache-busting query (`?cb=<n>`) — a new URL fetches a fresh document. Precedent: a preflight opened a card by its deep link and saw the old build's tabs without the feature's tab, while the root of the same host already served the new build.

## Design mock-ups

- **A design-tool MCP on a viewer seat has a hard call limit, and it runs out mid-round.** The node ids come in the brief — the manager collects every one of them from the task's description and its comments, where analysts add mock-ups later; fetch them in the fewest calls, at the needed resolution straight away (`maxDimension` = the `original_width` from the first answer), not at the default 1024. When the limit is exhausted, record which nodes are left and tell the manager in your summary — a screenshot from the user is faster than waiting for the reset, and asking for it is the manager's move.
- **A node from a link is often a board of several frames** (a whole flow): at the default size it is unreadable. Download it at its original width and crop the frames locally (`sips`, see «The page-scripting sandbox»), taking the crop coordinates from a small preview. The board's structure listing — one call, read from the file the tool saves, since a board's metadata runs to hundreds of kilobytes (`report.md`, «The design has no such screen») — answers two more questions with no per-frame calls: a frame's caption («… — field error») often sits in a neighbouring title frame rather than in the frame's own name, so captions are matched to frames by coordinates; and a text layer's name is its text, so captions, toasts and labels are read from the structure listing, with no code-generation call that may need a skill of its own.
- **The UI is checked against all three sources — the requirements, the attribute tables, the mock-up** — and every disagreement goes into the result with each variant (the rule: `report.md`, «The design has no such screen»); date formats, empty-value placeholders and status chips are where they differ most often.
