# Planning a round: scenario shapes

Read at step 3 of `../SKILL.md`, before writing `1-plan.md`. Each entry is a shape a scenario can take and what planning it wrong costs; the
precedent that closes an entry is what paid for the rule. **Read the file whole** — the value of the list is in the shapes you did not think
of, so do not grep it for the one already on your mind.

## Contents

Single entries first, then the **families** — one mechanism with its shapes under it. A shape is only readable through its head
entry, so a family is read whole or not at all.

**What the plan rests on**

- the task has NO requirements at all — the round's product is the question, and the defect criterion is fixed in advance
- a task that re-states requirements already tested (an MVP cut, a phase two) — re-rate the previous round's findings first
- the requirements were rewritten so that the PREVIOUS round's subject is cancelled — inventory what that round left behind
- a finding of the form «always / never» is only as wide as the inputs that round actually tried — and its constructive twin: where the collection is enumerable, take the verdict over the POPULATION
- a round spanning several identities is sliced BY IDENTITY, not by theme
- «prove the defect costs money» — aim at the counter that gates spending, not at spending the damage
- an operation that answers NOBODY yields no verdict about its permissions — say «not measurable yet»
- a stop rule for a sweep is phrased by the EXPECTATION, not by the response code
- a document referenced from the task — reach it yourself first, ask the user only for what you cannot
- several scenarios rest on one lever of the environment — verify the lever by a control experiment at preflight; check what the lever conserves, not only that it moves; and a lever HANDED OVER by the user is verified the same way, contract of use included
- a requirement joined by «and» is split into numbered sub-items when the requirement table is written
- which recon is allowed at all, and why the contract of an external API is pulled before anything else
- pull the contract with its TYPES — a composition without types sends the plan down a false branch
- a status claiming the manual pass is already done — check who moved it and when, or the mode is wrong
- recon already answered most of the plan — the plan becomes a hypothesis table, and the residue is sliced first
- requirements about filters, search or sorting — the contract predicts the section's main risk
- the fields the client requests ≠ what the server can filter or search by — closed by a probe
- a backend task — recon through the logs before the first expendable action
- an automation-only task whose feature shipped long ago — measure the coverage gap: live contract, existing tests, delta; ask FIRST whether the requirement is observable from outside at all; and the task's own QA checklist is dated evidence
- **The reference environment** — the build without the task is the only baseline: a refactoring task planned as a diff · a RECOMPOSITION, where it is mandatory and goes first
- **The order of the server-side checks** — one probe, read six ways: a permissions negative on a VALID payload and its control on a read · a junk sweep splits in two · the free negative matrix · a fixture that reaches a NEW guard · a borrowed object · proving the guard you lean on
- **The tracker is searched at step 1** — by the subject noun, closed tasks included: a comment pointing elsewhere · the task that OWNS the requirement · the task that HOLDS the list being retested · a search the tracker REFUSED
- **Dating the build** — the verdict belongs to a build and the tracker does not name it: an undated retest trigger · a stale environment behind the task's label · a redeploy mid-round · a service with no version endpoint, dated off a past execution · a deploy that also wiped the fixtures

**Scenario shapes that need planning of their own**

- «accumulate N events inside one pass of a worker» — batch limits, merging, aggregation windows; and flipping a setting inside a window of the process
- the round ADDS a precondition to its own fixture — re-classify every inherited probe before running it
- the fixture IS a stuck state (pending, hung, awaiting a third party) — measure its lifetime before slicing
- the check needs an ALREADY-ELAPSED state — an expired deadline, a spent quota, a used one-time code
- a requirement of the «no more than N per window» kind — plan against BOTH the sliding and the calendar reading
- the oracle is a count of records in an external journal — a webhook receiver, a delivery log, a queue
- a consequence derived from reading, not observation — a hypothesis with an expiry date, close it in the same round
- you do not know how the thing can be verified at all — phrase it as a question, not as a path
- the scenario needs a value the product's own users cannot enter — find WHERE it comes from before slicing
- expendable artifacts come from another step of the plan — a fallback table of what goes where
- a refusal observable only from the state the action destroys — API path or a second carrier
- the negative on a guard requirement SUCCEEDS — measure, in the same round, the chain the missing guard opens
- a step that needs a financial or credential-shaped value typed in — a human step, planned as one
- the condition cannot be reproduced — ask the user to MANUFACTURE the state before asking to mutate live settings
- the task description claims «the rest was checked and is correct»
- the document referenced from the task describes a DIFFERENT environment than the one under test
- one scenario's side effect destroys another's fixture — the order is load-bearing, and the plan says why
- overlapping operations on one object — plan them, they are where deferred-reconciliation defects live
- **The main run and its control** — a pair differing in exactly one condition: a branching rule in the docs · an artifact consumed by the first attempt · «does the path work» run twice · a non-deterministic defect · «type X does not work» · a filtered ZERO · a DEGENERATE oracle, including the zero-delta «it came back» · a recomputation with its cross-control
- **Before a requirement is planned as «not covered»** — every shape is settled by one cheap move: «we have no access to X» · no channel versus nothing to show · «there is no way to do X» · an unreachable screen · «works under degradation» · «it cannot be reproduced» · a property that kills a whole STATE

**Gates, budgets and the wording of restrictions**

- **The gate before an irreversible step** — the cheapest call that would have to work afterwards: a reversible destructive action · an operation that TURNS ON a mode · a scenario that costs money · a rehearsal on a free surrogate before the expendable is spent · a reverse whose precondition the forward step creates · an ADJACENT system's own preconditions · what the gate does not cover · a gate that stops the run, and «by default» instead of a ban

## What the plan rests on

### The reference environment

**A task whose requirement is «nothing should change» is planned through a build WITHOUT it, not by re-reading the requirements.** Find an environment running that build (a neighbouring env, the previous release, production) and make the main scenario a **diff of the observable result**: the same calls, the same exports, the same screens — field by field, column by column. The declared changes are listed in advance, and the verdict reads «the only discrepancies are the ones on that list». That is the only way to separate a regression from a **pre-existing** defect, and it also keeps the executor from false findings: in one session control experiments on the old build removed three discrepancies that looked like defects of the task (stale case expectations, «broken» totals with the criterion column missing, a control absent from someone else's cabinet). Require an explicit «as it was» column in the brief, and note the limit: the reference build changes too, so the diff carries a date.

**On a RECOMPOSITION the same environment is mandatory and goes FIRST — it is the only baseline there will ever be.** A screen relaid out, a table turned into a list, one control replaced by another, a payload restructured: the new state is on the screen and whether the complaint is gone is visible in one look, so the task reads as needing no baseline. That reading loses the round's second requirement — **nothing was lost on the way**. Only the old build says what «everything» was, and once the recomposition is deployed everywhere that list is unobtainable at any price. Enumerate the old surface **before** describing the new one, and make the verdict a mapping «every old element → where it lives now»; an element with no new address is the finding. The same read pays twice: comparing the served artifacts (bundle hashes, image refs, the stylesheet against the script) dates the fix from the outside and often gives the SHAPE of the change for free. Precedent: a layout round listed the control environment as an optional final scenario and it turned out to be the most valuable one — it dated the fix (the stylesheet hash was unchanged between builds, so the change was structural, not CSS) and yielded the 28-element baseline against which «nothing was lost» was proven item by item; without it the question would have stayed open permanently.

**When the task carries NO requirements at all — an empty description, no acceptance criteria, no comments, nothing but a title — the round does not verify, it RECORDS; and what makes that round productive is a defect criterion written before the executor starts.** The degenerate case of a `draft` verdict is not a weaker version of it, it is a different round: there is no expected result to compare against, so every observation is compatible with «works» and with «broken», and an executor left to their own judgment will supply the missing expectation from their own intuition and file it as a defect. Two moves keep the round from being either a rubber stamp or an invention. **State plainly that no verdict on the subject will be passed** — the round's product is a question to whoever owns the requirements, asked with numbers in hand — and say it in the brief, not only in the plan, because it governs what the executor is allowed to write down. Then **enumerate, in advance, the defect classes that survive ANY answer to that question**: internal inconsistency (components of one record computed from different inputs, an aggregate that does not reconcile with its parts), a divergence between what the system records and what it actually does, and the operation failing outright. Those are verifiable without an oracle, they are what the round can honestly deliver, and naming them converts «we cannot judge» from an excuse into a scope.

Two riders, both cheap and both easy to skip. The question is worth more with **the cost of each answer measured in the same round**: if choosing the other branch would require data the product does not store anywhere, that fact is discovered by reading the existing contracts and it often weighs more than the argument itself. And a round like this yields a case nobody can write — so do not create one, hand it over as a candidate with its expected result left open, and say in the report that the omission is deliberate; a TMS case written here would canonise behaviour that may be exactly the defect. Precedent: a five-month-old bug whose entire specification was its own title; the round measured what the system does, found zero defects against the pre-agreed criterion, and delivered the requirements question plus the finding that the alternative answer would need a field the product does not have anywhere outside one screen — which was the sharpest sentence in the report.

**A task that re-states requirements already tested — an MVP cut, a phase two, a «trimmed scope» — is planned in two motions, and the first one is re-rating the previous round's findings against the new text.** A trimmed spec is rarely just a subset: while it is being cut, it is also being reconciled with what the build already does, so requirements the previous round declared violated may now be written down as the intended behavior. Map the old findings onto the new text one by one before slicing a single scenario — each becomes «still a defect», «no longer backed by any requirement», or «survives in a narrower form». Only then build the coverage map (every FR/AC of the new text → pass / partial / not covered, with the evidence that supports it) and cut the round out of what is left. Skipping the re-rating costs twice: the round is planned around defects that are no longer defects, and the report hands the customer a verdict its own spec contradicts. **The requirements are also rewritten IN RESPONSE to a previous round's findings, and then a finding can be closed by an edit to the text rather than by an edit to the code — a valid outcome that must be reported as such.** Expect the analyst's note on a finding («fix this one») to mean either; read the new text before believing the note, because the same sentence often turns out to have moved the requirement to match the implementation. Two consequences: the round's verdict on such a finding is «closed by a spec edit, code unchanged» (say it plainly — the customer decides whether that was the intent), and the requirements rewritten around it usually bring NEW obligations the build never had, which is where the round's real findings come from. Precedent: of three retested findings one was closed by the rewritten acceptance criterion, one survived word-for-word into a stricter requirement, and the five clauses added around them yielded five new findings — the round's value was almost entirely in the new clauses, not in the three findings it was called for. Precedent: of seven criticals from the full-spec round, five were requirements in the MVP text — including one that the trimmed spec demanded verbatim — while the honest remainder of the round turned out to be the parts the previous run had never touched at all.

**When the requirements are rewritten so completely that the previous round's SUBJECT is cancelled, the round does not start with scenarios — it starts with an inventory of what that round left inside the product's own systems.** «Nothing to compare against» is the wrong conclusion to draw: the cancelled implementation is gone from the code, but the previous round's artifacts are still alive and still asserting a contract that will never exist — a committed autotest (usually parked as skipped, which is exactly why nobody notices it), a TMS case describing the dropped operations, a knowledge-base file stating their behavior as fact, rows in whatever registries track disabled tests and past sessions. Each one will be read by somebody as current. So list them before slicing anything, and put each to the user as a decision — delete, repurpose, or leave — because the answer changes the round's own work: a repurposed case is not created but rewritten, and a deleted test takes its helpers with it. The inventory is cheap (a grep for the dropped operation names across the test code, the case tracker and the knowledge base) and it is the only moment when the whole set is visible. Precedent: a round whose subject had been cancelled a week earlier found a skipped autotest on the dead API, its seven helpers, a TMS case, a knowledge-base file and a registry row — none of which the plan would have touched, and all of which the user disposed of in one question.

**A finding of the form «always / never» is only as wide as the inputs actually tried — and the coverage map inherits its error.** When a previous round wrote «the method always returns an empty list» after trying two of the three parameters the contract declares, the next round starts from a false constant: the plan drops the scenario as «known broken», and the untried parameter — the one the contract makes mandatory — is never reached. So when a past finding is phrased as a universal, treat it as a hypothesis over the inputs that round used, and put the untried input back into the plan as a scenario of its own. The same discipline applies forward: a universal claim in your own report is earned only by exhausting the contract's input set. **A tracker entry that contradicts such a claim is evidence, not noise:** when an existing task says «the check exists, the list is merely wider» and your executor writes «there is no check at all», the second statement is the one that outran its inputs — it was made from valid values only, and the input that would expose the check was never tried.

*The constructive twin of that rule: where the collection is small enough to enumerate, the verdict is taken over the POPULATION rather than over a specimen, and it is stated as a fraction.* The instinct is to pick one representative object, measure it carefully and write `pass` — which is correct and weak: a single match is compatible with a rule and with a coincidence, so the next reader (and often the same round, an hour later) spends effort deciding whether the one object was lucky. On an environment holding hundreds rather than millions of the relevant records, the whole set usually comes back in one or two listing calls, and cross-checking every one of them against its counterpart is a local computation, not extra requests. It costs less than the argument it prevents, and the verdict changes character: «99 of 99» names the exceptions if there are any, and where there are, they arrive pre-grouped — a handful of rows sharing one attribute, which is the diagnosis rather than a puzzle. Say in the brief which listing bounds the population and what the per-record comparison is, and require the fraction in the result. Two riders. The exceptions are the valuable half, so the verdict is written as «N/M, and the M−N are all of shape X» rather than as a percentage. And the move is only available while the population is genuinely enumerable — on a production-scale collection the same instinct produces an unrunnable plan, so the bound is checked (one listing with the total) before the scenario is sliced. Precedent: a brief asked for a projection to be compared against its source on one record; the executor spent three extra calls to compare all 99 records of that class on the environment, and the round's verdict went out as 99/99 by identifier and 85/85 by status, with the seven mismatches turning out to share a single status value — a fact no specimen could have produced.

**A round that spans several identities is sliced BY IDENTITY, not by theme — and the brief says what to collect before leaving each one.** Thematic slicing reads well in the plan («first the fix, then the permission matrix, then isolation») and is paid for in logins: each theme touches two or three roles, so the round zig-zags between sessions, and on an environment where switching identity costs a full login cycle that is the round's largest fixed cost. Worse, it silently strands data: identifiers that only one identity can read (another tenant's entities, an admin-only listing, a journal) are needed by a scenario that runs under a different one, and the executor discovers the gap after the session is gone. So order the scenarios by the identity they run under, put the identities in the order that makes each one's output available to the next, and enumerate in the brief — per identity — exactly which identifiers and snapshots to carry out before switching. Precedent: two executors in the same round independently raised the same complaint; in one pass a foreign-entity identifier was missing because only a privileged role can list it and the round had already left that role, and the decisive negative went unmeasured.

**A scenario meant to prove that a defect has MONETARY consequences is phrased as «show that the counter the defect moves is the same one that gates spending», not as «spend the damage».** The instinct — inflate a balance, then try to use the inflated part — is unrunnable wherever the object carries a large legitimate balance: the sanctioned damage is a rounding error against it, and no spend can be attributed to the inflated portion. The counter-identity question is answerable on any background, with reads plus one refusal: the operation debits counter C, the defect credits counter C, and a request above C is refused by name. That chain is what turns «the number on a screen is wrong» into «the money is real», which is the sentence that sets the finding's priority. Precedent: «spend the phantom balance» was impossible against a ~200 000 unit seeded balance, and the same question was closed by three measurements around the counter that gates payout creation.

**An operation that answers NOBODY supports no conclusion about its permissions — and the round must say so instead of inferring one.** When a call times out or 502s under every role tried, «it was not refused» is not evidence that no guard exists: a guard that admits the role and a guard that is absent produce the identical observation, because the failure happens after the decision. The tempting write-up — «the operation is not covered by the role check», i.e. a hole in the access model — is exactly the one the data does not support. Record the measured part (nobody gets an answer; the durations, which under a fixed gateway timeout land within a couple of percent of each other) as a functional outage, and mark the permissions question **not measurable until the outage is fixed**, with the retest named. The distinction matters because the two readings have different owners: an outage goes to the team that owns the service, a hole in the access model to whoever owns the guard. Precedent: a round nearly filed «this operation bypasses the role check» from a single unrefused call, and the control under a privileged role returned the same 90-second timeout — the finding turned into an outage report, and the permissions question stayed open honestly.

**A stop rule for a sweep is phrased by the EXPECTATION, not by the response code.** «Stop on success» reads as «stop on anything that worked», and on a sweep that legitimately includes permitted operations it fires on the first correct behavior: the run halts, the remaining blocks go unmeasured, and the report carries a false alarm. Phrase it as «stop on a success from an operation this role must NOT be able to call» — and add the counterpart the executor otherwise has to invent mid-run: a success from an operation the role IS allowed to call is a valid measurement, note it and continue. Precedent: a stop rule written by the code cost a round two of its six blocks — the trigger turned out to be an operation working exactly as the requirements demand.

**A document referenced from the task is part of the requirements — and the two ways of reaching it produce different rounds.** SKILL.md
step 1 carries the procedure; these are the shapes it comes in.

*The document you can reach yourself.* A one-line task plus a link to a spreadsheet, a doc, a design file or a wiki page reads like «there
are no requirements here», and that reading sets the round's strictness: a `draft` verdict tells the executor to guess expectations where the
document may state them verbatim. Try the session's own connectors before rating anything — one call. Precedent: a task whose whole
description was one sentence and a spreadsheet link turned out to be **spec-grade on the composition of fields**; the sheet listed every
required field of every level by column, plus a worked example with numbers, and the entire requirements matrix of the round came from it —
rating the task `draft` would have cost most of the findings. Two riders. Such a document routinely **contradicts itself across its own
sheets or pages** (a normative field list against an illustrative mock-up): that is a question for the analyst, settled before the finding is
written, not a defect. And a field the document names but the product has no data for is still a requirements gap — the verdict is «absent»,
with the empty data source noted as the mitigating half and addressed to whoever owns it.

*The document you cannot reach* (an MR/PR description behind a login, a dashboard, an internal log). Ask the user once, at the start, before
slicing the plan: they almost always have access, and the composition of a fix redefines the scope of a retest. Precedent: a «see the
description on the request» that sat behind a password cost a black-box round on one bug — read afterwards, the description listed **five**
closed requirements and two deliberate deviations, and the round's scope would have been different.

**When several scenarios rest on one lever of the environment — a knob that induces the condition under test — that lever is verified by a control experiment BEFORE the plan is sliced, not while the round is running.** The shape: the requirement is «behaviour B does not depend on slow/failing/degraded X», the only way to observe it is a setting that makes X slow or fail, and the plan quietly assumes the setting works. On a shared test environment such knobs rot silently — the endpoint still accepts the value and echoes it back, while nothing downstream reads it any more. The executor then discovers it mid-round, after the scenarios have been ordered around it, and the requirement ends up not merely failed but **unverifiable**, with no oracle left to replace it. The check is one call plus one observation (set the knob, perform the cheapest operation it should slow down, look at the duration) and it belongs to the manager's preflight, next to «is the feature deployed». Two outcomes, both useful: the lever works and the plan stands; it does not, and the scenarios resting on it are re-planned or declared not covered **before** the executor spends the round on them — and the dead lever itself becomes a side finding, because the next session will plan against it too. Precedent: three of eleven scenarios rested on a mock provider's response-delay setting. The endpoint accepted the value and echoed it back, and nothing downstream changed — so the round wrote the knob off as dead and closed two requirements as not covered. Both halves of that verdict were wrong: the environment under test routed its provider traffic to a **different instance** of the mock (a per-environment split that had been built but never deployed), and the value was in seconds while every caller assumed milliseconds, so the «test» value had in fact asked for a two-minute delay and hit a proxy timeout. The user overturned it after delivery. The control that would have settled it at preflight is the same one that settled it afterwards, and it is end-to-end by construction: set the knob, perform a real operation that must slow down, time it — never «the setting endpoint returned the new value», which is exactly what both errors survived.

**A lever that works perfectly can still be unable to produce the state the scenario needs — check what it CONSERVES, not only that it moves something.** The entry above is about a dead knob; this one is about a live one aimed at the wrong quantity. The plan names an operation that demonstrably changes the value under test («move money between the wallets», «reassign the item», «switch the owner») and hands it over as the way to reach a state — but a transfer conserves the total, a reassignment conserves the count, a rename conserves everything but the label. So «empty **both** wallets by converting between them» is not hard, it is arithmetically impossible, and the executor finds that out with the fixture already half-prepared. One question while slicing settles it: which quantity does the scenario need changed, and does the lever change *that* one or merely redistribute it. Where it only redistributes, the state is usually reachable from the other side — make the threshold unreachable instead of the resource absent. Precedent: a brief offered currency conversion as the way to drain a merchant's balances to zero; conversion preserves value between the two wallets, and the scenario was closed by the mirror move — an order for a deliberately unaffordable amount against untouched balances.

**A lever HANDED TO YOU by the user is verified at preflight exactly like one found on the environment — and a credential is only half a lever.** The two entries above are about knobs that rot or aim at the wrong quantity; this one fails through the manager's own deference. The shape: the start question asks for the access that would unblock a requirement, the user supplies it — a key, a secret, a token, a console login — and its authority silently exempts it from the control experiment. It should not: the value may belong to another environment, to another field of the same config, or to a generation the deployed service no longer accepts, and none of that is visible from the string. Worse, a credential is not a lever by itself. It is exercised through a **contract of use** — which header carries it, which bytes it signs, which algorithm, whether a timestamp participates — and that contract is a second thing to ask for, in the same breath as the value, because without it the key cannot be tried even once. Ask for both, exercise both at preflight against the cheapest call that must succeed, and only then let the plan call it the round's main resource. Where it does not work, the two causes — wrong value, wrong contract — are usually indistinguishable from outside, and that is itself the finding to deliver: one answer from the developer closes both. Precedent: a secret for verifying an inbound vendor webhook was supplied by the customer and made the backbone of the plan; at the executor it turned out to validate nothing, across every standard signature form and even against a byte-for-byte genuine vendor body, and half the round's requirements stayed uncovered — the contract of the signature had never been requested alongside the value, and one control call at preflight would have moved that discovery before the plan instead of after it.

**And before promising an AUTOTEST on the feature, ask where the lever comes from — a fixture someone configured by hand is not infrastructure, and it disappears on the next redeploy.** A manual round only needs the lever to exist today; a test needs it to exist on every environment, on every run, after every deploy. The two questions look the same and are not, so the gap surfaces at the worst moment — the round has already delivered a verdict, the customer has already asked for automation, and the environment comes back without the thing the whole feature runs on. Establish provenance while planning the manual round, at the cost of one question to the developer or one look at whether the object is in the migration: is this part of the environment's standard configuration, or did someone create it for this task? Where it is hand-made, say so in the report next to the verdict — the feature is not testable repeatably until its configuration ships with it — and treat that as a finding about the delivery rather than a note about the round. Check, too, whether you could recreate it yourself: an admin API that creates the object may leave it non-functional (the part that matters lives in a field the API does not expose), and an endpoint that silently ignores the field you need answers `200` while changing nothing. Precedent: the provider mids the whole feature depended on had been created by hand on one environment, vanished in a redeploy two hours after the round, and could not be rebuilt through the admin API — the created mid had no integration config and every payout hung in retries, so the automation the customer had just asked for became unwritable through no fault of the round.

**A requirement joined by «and» is split into numbered sub-items when the requirement table is written, not left to be split by the verdict.** Demanding a `partial` verdict with a breakdown at acceptance catches the problem late: an executor reading one line reads one expectation, closes the half that is cheap to observe, and reports `pass` — the second half is not refuted, it is never approached. Splitting happens at step 1, where the requirements are transcribed: every clause with its own observable outcome becomes its own row, and the row that needs a control experiment becomes visible as a row rather than as a subordinate clause. The `partial` verdict then covers the residue — compound requirements you failed to notice — instead of carrying the whole load. Precedent: «the link carries the identifier **and** the player's arrival starts the search» went into the table as one row; the first half was confirmed in the first minute, and the second — the mechanism the whole task was about — was only reached because the executor ran a control experiment on their own initiative.

**Recon that is not about «how it was implemented» stays useful and is allowed:** is the feature deployed to the environment (a «the fix
isn't on the env» blocker found before launching the executor saves the whole run), and what is the contract of an external seam (callbacks,
integrations, webhooks) when the scenario cannot be assembled without it. The project's techniques for such recon are in the profile,
Environments section. For a task involving an external API, **the machine-readable contract is pulled as the very first step, before slicing
the scenarios**: the list of implemented operations instantly splits the plan into «there is something to check» and «closed by the single
fact of absence». Precedent: «not one of the nine methods exists in the contract» closed ~20 requirements in two minutes, while three
«ordinary» scenarios each yielded 3–5 findings — the scope estimate from the spec was wrong in both directions at once.

**Pull the contract with its TYPES, not just the names of its fields and operations — a composition without types sends the plan down a false branch.** The list of fields answers «is there a place for this requirement»; the type of each field answers «what can it hold», and the second question is the one that slices the scenarios. Two shapes cost a whole scenario when skipped: a field declared as an **enumeration** cannot carry the values a neighbouring contour uses, so an entire line of «what happens on an unknown value» is moot on the server side; and a field that looks scalar may be a rich nested object that already implements the requirement you were about to file as missing. Both come from one deeper introspection pass at recon time. Precedent: recon handed the executor a field list, the plan sent them to hunt for a missing fallback on unknown statuses — and the field turned out to be a three-value enumeration normalised server-side, while a neighbouring «just a field» held the fully populated event feed the main requirement asked for.

**A tracker status that asserts the manual pass is already done is evidence only when a QA trace stands behind it — check who moved it and when, before choosing the round's mode.** Status→mode mappings assume the status was set by whoever did the work, and on a real board that assumption breaks constantly: a manager sweeping the backlog moves items into a testing-done state months after the code merged, and nothing in the value itself says so. The two readings buy opposite rounds — «the manual verdict exists, only automation is left» skips bug hunting entirely, which is exactly what a never-verified fix needs most. One read of the status history answers it (who moved it, and when relative to the merge), and the absence of any QA artifact — a comment, a case, an earlier session — settles it; say the answer in the report, because it also explains why the round was run the way it was. Precedent: a task had sat in an automation-only state for a month, moved there by a manager five months after the merge, with no QA comment anywhere; run as a full manual round instead, it produced a Critical that the automation-only mode would never have gone looking for.

**When recon has already answered most of the plan, the plan becomes a table of HYPOTHESES rather than a table of routes — and the round's
value moves to independent confirmation plus the residue recon cannot reach.** On a research or decision task (no acceptance criteria, the
description is an analysis with a proposal) a couple of cheap reads often close most of the scenarios before the brief is even written.
Handing those over as conclusions wastes the executor: they will paraphrase you. Handing them over as numbered hypotheses — each with the
channel it was taken from, the date, and the formula «refuting it is the round's result, not your mistake» — buys a second pair of eyes on
facts the report will rest on, and it works: in one such round the executor refuted one hypothesis of eight, and the refuted one was the
task's own claim about itself. Two obligations come with the shape. Decide explicitly whether any **manual residue** is left at all
(a sanctioned mutating probe, a UI control, a depth of evidence recon could not reach) — if none is, do not launch an executor, file the
recon as its own session file and say in the report why there was no manual run. And slice the residue first, not last: it is the only part
of the round that can fail.

**Requirements about filters, search and sorting: the contract is pulled by the same motion, before slicing the scenarios.** The set of
filter parameters in the request splits the requirements into «this could be server-side» and «the server has none of it», and the second
immediately names the section's main risk — selection and sorting over an already-loaded page, which looks fine on page one. Precedent: a
list's contract turned out to be a search string plus limit/offset, which predicted a Critical before the run (a status filter that returns
nothing while matching records exist) along with the per-page sorting.

**The fields a client REQUESTS say nothing about what the server can filter or search by — those are different mechanisms, and conflating
them plants a false gap in the plan.** The reasoning feels airtight: the list request does not ask for the related entity's name, therefore
searching by that name cannot possibly work, therefore the requirement is unmet before the round begins. It is wrong whenever the search runs
server-side: the server joins whatever it likes and never has to return it. The same holds in reverse — a field present in the response is no
evidence that it can be filtered or sorted on. So a requirement about search, filtering or sorting is closed by **one probe against the live
endpoint**, never by reading the client's query; recon may raise the hypothesis, and the brief hands it over as one, marked «refuting it is
the round's result». Precedent: a round's central hypothesis said searching by the related company's name was impossible because the page
never requests that name — one call refuted it, the server matched on it with partial matching, and the requirement came back `pass`.

**For backend tasks, recon through the profile's `logs` is the brief's first step — before the first expendable action on the environment.**
Traces and execution histories hand you the constants (timeouts, TTLs, limits), the step names and the feature's actual shape, from which it
is immediately clear where to aim the scenarios. That is not reading code — it is the system's observable behavior. Precedent: the
hypothesis of a Critical was born from the histories of two workflows read before the first touch of the environment, and was confirmed
afterwards with two requests — whereas head-on, the same scenario looked like a tautology.

**An automation-only task whose feature shipped months ago is planned as a measurement of the coverage gap, not as a hunt for bugs.** Such
a task sits in an automation queue because the manual verdict was passed long ago; the product has been live since, so the interesting
question is not «does it work» but «what, exactly, does no test measure». Take the three readings in order: the **live contract** (one
read of the relevant mapping — permissions, fields, endpoints — from the environment itself), the **tests that already touch the area**
(grep by endpoint and by case id), and the **delta** between them. The delta is simultaneously the scenario to automate and a tech-debt
list, and the second half is usually the more valuable: tests drift away from a contract that kept moving after they were written, and the
drift is invisible until someone puts the two side by side. Two things to look at in the same motion, because they cost one grep each: does
the existing test carry a REAL link to its case (a legacy tag that no longer binds is indistinguishable from a link until you check what the
TMS receives), and does the framework's own table of expectations still match what the environment returns. Precedent: a permission gate
shipped six months earlier was a two-step addition to an existing test, while the same pass found the test reporting to no case at all and
the framework's permission table missing two rights that the environment had had for months.

*The automation decision starts with ONE question — is the requirement observable from outside at all — and a «no» settles it before cost or size are weighed.* The usual order is the opposite: the manager slices what to automate, estimates the run, argues the feature's size, and only at the automator's brief discovers there is nothing to assert. Ask it first, because it is the cheapest of the three and it is the only one that can end the discussion on its own: name the response the requirement would show up in, and read a real one — a recent run log holds full request/response bodies for exactly these endpoints, which beats reading the implementation and beats remembering the contract. Two shapes of «no» recur. The requirement is **internal by construction** (an ordering, a scheduling interval, a queue's fairness): nothing in any payload names it, and the only oracle is a distribution in the logs, to which a test framework asserting API responses has no channel. Or the field that looks like the oracle is about a neighbouring mechanism — a counter of *send* attempts standing in for a counter of *status polls* — which a single real response settles and a plausible name does not. Where the answer is «no», say so as the first line of the automation section: a verdict resting on observability is stable, whereas one resting on the price of a run invites the counter-offer of a cheaper run. And name, separately, whichever underlying mechanism turns out to be covered by no test at all — that is a real gap, it is usually not this task's feature, and it is the user's call, with its standing cost attached, not a silent omission.

*The task's own record of what QA already did is DATED evidence, and the date that matters is the merge — not the comment's.* Such a task
usually carries a tidy checklist left by a past round («autotest: <name>, case: <id>», both ticked), and it reads as the answer to the
question the round was brought with, so the round starts by opening those two artifacts. They can be about a build that never shipped: where
the task's own merge-request list shows one request **closed** beside another **merged**, the implementation was replaced, and a checklist
written between the two points at the abandoned one. The tell is free — it is printed in the task's header next to the links — and the
correction is one grep: find the coverage by the case id embedded in the test code and by the feature's mechanism, not by the name the
comment gives. Do it before planning, because every downstream artifact inherits the wrong pointer: the round verifies a neighbouring
scenario, the report cites a case that describes something else, and the tracker comment confirms coverage that does not exist. And say in
the report which pointer was wrong — the stale line stays in the task otherwise, ready for the next round to follow. Precedent: a task's QA
checklist named a test and a case for a flow whose merge request had been closed a week later; the shipped request implemented a different
flow, its real coverage sat under a different case id, and the case the task named turned out to describe an unrelated failure mode. The
mirror case is cheap to close and easy to leave hanging: the checklist predates the merge by days because the round ran against the branch
build, and the merged request is the same one — then the gap is not «stale evidence» but «never re-checked on the mainline», and it closes
with a fresh INDIRECT observation (a later session's note in the knowledge base that the mechanism still behaves that way on the current
build) far more cheaply than with a re-run. Say which of the two it was; silence reads as the round having missed the dates.

### The order of the server-side checks

**Before a negative is sliced, take the ORDER in which the server checks things — one probe answers it, and three separate failures come out of never asking.** A negative aimed at a guard that runs after something else proves nothing about the guard; a probe that is «safe» only because an earlier check refuses it starts writing the moment that check is satisfied; and a guard standing behind an older validation cannot be observed at all. The six entries below are that one probe, read for six purposes.

**A negative about permissions runs on a VALID payload with a deliberately null side effect — and its companion control runs on a READ endpoint.** Where field validation runs before the role check, a deliberately broken payload returns the same error under every role: the whole matrix comes back «not proven» and the round pays for the logins on top. What works under either order is a valid request whose success would create nothing new — a duplicate of an entity that already exists, or an operation aimed at the round's own expendable object; then a refusal is a verdict about permissions and an unexpected success is itself a finding. The control that proves «the permission layer is alive» belongs on a protected read: a mutating control runs precisely in the world where the guard may be broken, so it performs the mutation itself in the one case it exists for, while a read gives the identical `403` at zero cost and throws in a passing control for free. Name the read endpoints in the brief. Precedent: a matrix designed on invalid data had to be rebuilt mid-round once recon showed validation running first — on a duplicate email plus operations against the round's own probe record, it closed the requirement across two roles and four operations without touching a foreign entity; in another round the executor swapped the brief's «create a transaction» control for three protected reads on their own initiative.

**«A junk payload changes nothing» holds only where a guard stands in FRONT of the operation — so a sweep across ALL operations splits in two before it runs.** On an operation open to every role the guard is legitimately absent, the call reaches the handler, and whatever you sent becomes the new value. Operations addressed by an identifier (pass a non-existent id) are safe under any role; operations that write content are safe only under a role the guard rejects, and for the roles it admits they leave the sweep or become an idempotent call rewriting the current value. Decide what counts as junk in the same motion: for a non-null string type an empty string is **not** junk — that type rejects only null, and the server will happily store `""`. Precedent: a sweep across every mutation of a contour ran clean on 23 of 25 operations and then wrote an empty name onto a live account, through the one operation the spec requires to be open to all roles.

**Where the guard under test is checked BEFORE an expensive one, the negative matrix is free — plan the input to fail on a LATER check.** Vary exactly the argument under test and choose everything else so the positive branch never reaches creation. Precedent: a budget of «up to three junk applications» went unspent — the guard is checked before capacity, so four calls at a deliberately unfundable amount closed the item and left the environment untouched. Where the guard comes later, budget the expendables and the cleanup honestly.

**When the question is «does a NEW guard exist», the fixture has to let every OLDER check pass.** The most natural fixture is the most useless one: a blank object satisfies the requirement's own wording and therefore trips whatever validation stands earliest, returning one identical refusal to every probe — which reads as coverage while proving only that some check exists. Ask which fixture reaches the check under test (everything else valid, only the condition under test not), and where the environment holds none, say so in the plan — «this round needs an object with X approved and Y missing» — as a candidate for the start question. On the fixture actually used the verdict is «no sign of the guard», never «the guard is absent». Precedent: a blank company answered all 17 probes with the same pre-existing refusal about a missing prerequisite, masking the validation of the amount, of the payment details and even of the operation type; the only place the new guard could still be observed was a draft-creation call that validates nothing at all.

**Borrowing an object that already HAS the precondition is free, and it usually answers a different question.** Shared environments accumulate objects other people brought to state X, and borrowing one spoils nothing, since the probe is expected to be refused. But the borrowed object differs from your fixture in more than the attribute you care about, and the difference usually includes **the very precondition the requirement is about** — a guard that fires only when something is missing does not fire where it is present. So the borrowed measurement proves the ORDER of the checks and the TEXT of the refusal, never the guard's absence: write that boundary into the verdict and keep the original fixture in «not covered» with the one step that would close it. Precedent: an executor blocked from creating a wallet borrowed a company that already had one and recovered the round's decisive measurement — and the manager still had to correct «the guard is absent» to «no sign of the guard on a company whose details are filled in».

**And the guard you lean on must itself be PROVEN before the plan rests on it — otherwise the «safe» probe is the mutating one.** Everything above buys safety with a check you assume exists; if it is missing, the first negative creates a real entity, and on an irreversible operation that burns the destructive budget in one call. Prove it by a reading route — the contract, an existing pair of entities that violates it, a rejection observed earlier; no reading route means the probe counts as mutating and needs the user's decision, not a plan item. Phrase it in the brief as «the check may not exist at all» rather than «the question is only the order of the checks», which reads as a guarantee and stops the executor from pausing. Precedent: a negative planned on a deliberately taken unique identifier returned 200 and created a second entity with a duplicate identifier — no delete, no deactivation, no rollback; the assumption behind the plan was the round's Critical, and the whole negative matrix stayed uncovered because every further probe cost one more permanent entity.

### The tracker is searched at step 1, before a single scenario is sliced

**The task you were handed is rarely the only one that speaks about its subject, and the neighbours change what the round is reporting — so search by SUBJECT, at step 1, including everything already closed.** Searching by the defect's own words finds nothing: a neighbouring task is titled in the vocabulary of the feature, not of the bug. Search by the subject noun of the requirement (screening, invoicing, notifications, refunds, limits) and read what comes back. Three shapes turn up, and each one rewrites the plan rather than the bookkeeping:

- *A comment on a finding points somewhere* («duplicate of task N», «see task M»). The task it names often carries the requirement the finding lacks — and if it is Done, the round stops asking «what should the behavior be» and starts saying «the requirement is written, the work was closed as delivered, the product does not have it». Unfold every such pointer whatever its age, and re-rate the verdict on the requirements afterwards: what you rated `draft` from the spec at hand may be `spec-grade` two links away. Precedent: a «duplicate of N» from two months earlier led to a closed task whose attribute table demanded, verbatim, the very state the product was missing.
- *Nothing points anywhere, and a neighbouring task OWNS the requirement* — often the opposite requirement, linked by neither relations, nor parentage, nor a mention. The verdict can invert: what the round was about to file as «the fix was forgotten» turns out to be the verbatim implementation of a closed task's acceptance criterion, and the finding becomes «two requirements contradict each other, one of them is being accepted right now». And the plan shrinks — a branch built to prove the missing behaviour, often the one needing the user's sanction for a destructive probe, stops being necessary. Precedent: a retest of «editing is unavailable» was planned around writing to a live entity and a question about which fixture to burn; the owning task, found only at acceptance, required that exact unavailability and had been closed weeks earlier — the whole destructive branch had been moot from the start.
- *The round retests a LIST of findings, and something HOLDS that list.* Findings recorded as a comment get promoted into a follow-up task («fixes for X», «remarks on Y») whose description is often nothing but a link back to that comment — which is exactly why a keyword search misses it. Found, it changes the report's sentence from «we discovered five defects» to «the follow-up task has been sitting untouched since <date>», which has a different owner; and it changes where each finding goes, since an already-filed one leaves the findings table for a line beneath it. Precedent: five findings were retested as if fresh, and the search at acceptance turned up a `TODO` task created for exactly that comment four and a half months earlier, with no assignee and no comments — that fact became the report's headline and shrank the findings table to a single row.

Done at acceptance instead of at step 1, all three still pay — but the round has already been planned, sanctioned and run around the wrong premise, and the report has to be re-framed. The same search runs a second time before publication, by the OPERATION's name rather than the subject: that half is in `report.md`.

**A search the tracker REFUSED is an unperformed search, and it must not be written down as «nothing found».** Trackers throttle: a cross-project query answers «this endpoint has been requested with the search argument too many times», a listing times out, an API returns a partial page. The refusal arrives in the middle of a sequence of queries whose other members did answer, so it reads as one more empty result — and the conclusion that goes into the session file is the one the answered queries support. Nothing marks it afterwards: «related tasks: none» looks identical whether it was established or merely not contradicted. Record such a query as **open**, name what it was going to ask, and repeat it later in the round, when the throttle window has passed and — better still — with the vocabulary the measurements have since produced. Precedent: a cross-project search hit the rate limit at step 1 and the round recorded that no related task existed; the same words, retried at acceptance, found two open tasks describing the very contour under test, one of which documented the limit the round had just spent its time measuring — the report's whole frame changed from «we discovered this» to «the team knows, and here is what is new».

### Dating the build the round runs against

**The round's verdict belongs to a build, and nothing in the tracker establishes which one — so date the served artifact yourself, before the executor is launched.** Read what the environment actually serves: the index page and the bundle for a frontend, the image or deploy ref for a backend. Three decisions come out of that one reading.

**A retest whose trigger the tracker does not date is dated by the distribution instead — and the same motion slices the round.** When the status has not moved and no comment says «fixed», do not fall back to «the user asked, so we re-run everything»: a build newer than the previous round IS the trigger and belongs in the report, or the verdict floats free of any build. Then grep the served bundle for the strings and markers of **each open finding** and you have a per-finding hypothesis — «structurally fixed» / «untouched» — before the executor starts, which turns «retest the fixes» into a table of what to prove and what to refute. Hand each one over with «refuting it is not a verdict, settle it by behavior». Precedent: the tracker was silent for three weeks, the served build turned out to be from that same morning, and four markers grepped out of it predicted three of the four outcomes exactly — the fourth (a tooltip present in the bundle but never reaching the UI) was refuted by behavior, exactly as the caveat allows.

**The environment named by the task's LABEL may be running a build weeks old — where it is stale, the choice of environment is a start question, not a decision somebody already made.** A label is set when the task is written and never revisited, while environments stop being deployed to. The labelled one carries the build the feature was developed against and its fixture history; a freshly deployed one removes «maybe the fix never reached this box» from every negative verdict. Both belong in the question with their prices, and it costs one line before the launch — asked after, it arrives as a scope change with the measurements split across two builds. **When the environment does change, rebuild the fixture table in the same motion and say which requirements become unverifiable**: fixtures are a property of one environment's data, so an object of the right age, status or shape does not migrate. Precedent: the fingerprint showed the labelled environment had received no successful deploy for a month; the round was launched on it anyway, the user redirected it after the executor's first step, and the only fixture in the project old enough to test a 30-day window stayed behind — the requirement it served ended the round uncovered.

**A shared environment gets deployed to mid-round, without notice and often with nothing to date it from the outside**, so half the UI observations describe one build and half another with nothing in the result to show it. Record the fingerprint at the start **and re-check it before writing down any UI finding**, not only at the ends; know the symptom of a swap (a blank page while the API answers normally, plus a syntax error on an asset path — the cached document is pulling a chunk that no longer exists); and state in the report which observations were taken on which build, noting that server-side measurements are unaffected. Precedent: a candidate defect («a computed field renders as an ellipsis instead of numbers») was withdrawn after a control run gave correct values to the last decimal — the first observation had come from a stale chunk, and the same round later showed the blank page outright.

**On a service with no version endpoint, «is the fix deployed» read from a HISTORICAL execution dates the build at that execution's moment, not now — and a hypothesis built on it can invert the round's verdict.** Backends rarely publish a version the way a frontend publishes a bundle hash, so the manager reaches for the nearest dated artifact: an execution history, a job record, a worker identity stamped on a past run. It is genuine evidence and it is evidence about the past — a deploy landing between that execution and the round replaces the very thing being judged, and nothing about the reading announces its own age. The failure is not a stale fact but an inverted round: the recon concludes «the refactoring is not on the environment», the plan is sliced around proving it, and the executor's first controlled action shows the opposite. Two moves keep it honest, both free. Take the fingerprint from an execution **the round itself causes**, so it is stamped by the run rather than inherited — usually the same call that opens the main scenario. And hand any fingerprint older than the round over as a *dated observation with its timestamp in the sentence*, never as a constant of the brief, with the standing instruction to judge by behaviour rather than by agreement with the table. Precedent: recon read the worker identities off an execution three hours old and raised «the change is not deployed» as the round's central hypothesis; the service had been redeployed in between, every worker's identity had changed, and the executor refuted the hypothesis on the first scenario — the brief's own line «verify by behaviour, not by matching this table» was what stopped the round from being written up backwards.

**A deploy that is FRESH dates more than the code — it usually reset the environment's data, so the fixtures named in the brief are dead before the executor opens it.** The reading that dates the build is taken for one purpose («is the fix in this image») and answers in the affirmative, which closes the question; the same timestamp carries a second fact nobody asks it for. A deployment on a shared test environment commonly reseeds or wipes its data, so every entity the plan selected — accounts harvested from a previous run's artifact, objects picked by age, an id pasted into the brief — stops existing at exactly the moment that makes the code verifiable. The two facts arrive together and pull in opposite directions, which is why the second one gets lost: the manager reads «the build is from this morning, excellent» and writes a fixture recipe whose source was compiled yesterday. The symptom reaches the executor as an authentication or lookup failure on the first call, and it is indistinguishable from the ordinary «that entity is stale» pitfalls the profile already warns about — so it is diagnosed, not recognised, and the round pays the diagnosis. One clause in the brief closes it: when the deploy is newer than the source the fixture recipe draws on, say so, and name the LIVE registry (a listing endpoint, an admin view) as the first source with the artifact demoted to second. The discriminator is worth naming too, because it is the same call: a listing that does not contain the candidate proves the reset rather than a dead entity. Precedent: a round dated its build to a deploy four hours old and confirmed the code was in the image; the same deploy had wiped the environment, every account in the run-artifact the brief pointed at answered an authentication refusal, and the executor spent the diagnosis before recovering the fixture from the admin listing — where all of that environment's accounts turned out to have been created in the twenty minutes after the deploy.

## Scenario shapes that need planning of their own

**A scenario like «accumulate N events within one pass of a periodic worker» (batch limit, merging, deduplication, aggregation window) is
planned together with alignment to the tick** — otherwise it checks something other than what was intended, and a failure reads as «did not
reproduce». A burst of operations smeared across seconds lands on both sides of the tick and produces partial groups: require the brief to
measure the worker's phase (pass times in the logs) and the «operation → record appears in the queue» lag, then start the burst so that all
the records land inside one interval. Precedent: 12 finalizations drifted apart by 2.63 s and gave 5 + 7 instead of «10 + 2», leaving the
batch limit unverified; a tick-aimed burst of 13 gave exactly 10 + 3 on the first attempt. It is also the only way to tell «the limit does
not work» from «the events fell into different passes».

**The same arithmetic governs a plan that FLIPS A SETTING inside a window of the process — and there the two numbers usually sit in the plan
already, unmultiplied.** The shape is a determinism recipe: «let phase one pick the mid / route / branch, then switch the setting so phase two
picks the other one». It is the right idea, and it is unrunnable whenever the setting's propagation lag exceeds the gap between the phases —
the switch lands after the decision it was meant to steer. Both numbers are cheap and are normally already written down (the profile states
the lag, the knowledge base states the timings), so the failure is not ignorance but never having put them side by side: the manager writes
the recipe, the executor discovers mid-round that the window is shorter than the lag and has to invent a replacement configuration on their
own budget. Multiply them while slicing, and where the lag loses, choose a configuration that needs **no** switch at all — usually a different
combination of what is already enabled. Precedent: a plan told the executor to enable a second provider «after the first split appears»; the
gap between splits was ~22 s against a ~30 s propagation lag for the flag, and both figures were in the brief, in different sections.

**A scenario whose own RUNNING TIME approaches the lifetime of the access it needs is planned with both numbers written side by side — and the renewal placed INSIDE the scenario, not around it.** Both figures are normally known before the round: the profile states how long a session survives, and the pipeline's duration is either measured or estimable from its steps. They are never multiplied, because they live in different sections of the brief — one under access, one under scenarios — so the executor meets the collision at the worst possible moment, in the middle of an irreversible sequence, where renewing costs a one-time credential and the recovery competes with a process that does not wait. Put the scenario's duration next to the window, say which stretch may not be interrupted, and instruct the executor to renew access BEFORE entering it rather than when it fails. Precedent: a rotation pipeline ran ~20 minutes with signing against a session lasting ~40, and the figure was in neither the plan nor the brief — the executor measured it on the way and got through on the luck of the timing.

**When the round CHANGES a precondition of its own fixture, every planned probe has to be re-classified «will be refused» / «will create something» — the old classification is void, and the barrier that made a probe safe is often exactly what the round removed.** The shape is specific to multi-round work: round N measures on an object that lacks something, and every probe comes back refused by the first missing prerequisite; round N+1 supplies that prerequisite to reach the check behind it — and the probes inherited from the earlier round are no longer refusals, they are writes. The executor carries the old expectation across because it was true twelve times in a row, and the budget of expendables blows in a call nobody meant to be a mutation. So make the re-classification an explicit step of the brief for any round that adds a precondition: list the probes, mark each one by what refuses it NOW, and say which of them consequently need the user's sanction. In the same pass, note the corollary: a probe that only remains safe because of a barrier the round is about to remove was never a safe probe, it was a lucky one. Precedent: a probe with a valid operation type had been refused by the missing-wallet check through two rounds; the round that added an approved wallet ran the same probe unchanged and created a second live order, one over the sanctioned budget.

**When the fixture the round needs IS a stuck state — a record awaiting a third party's answer, a job pending, a transfer hung — establish how long that state actually survives BEFORE slicing the scenarios, because something in the system is probably closing it for you.** The plan's language gives the trap away: «hangs forever», «stays until someone intervenes», «will never resolve on its own». That is a claim about the absence of a mechanism, and it is usually inherited — from a case written when the mechanism did not exist, from a recipe that worked once, from the very feature under test being described as «the only way out of this state». Meanwhile reconciliation is ordinary engineering: a poller asks the third party again, a sweeper ages records out, a retry closes what the callback never confirmed. The state then has a lifetime, the round has a window, and every scenario built on «take your time, it will wait» is silently racing a timer.

Two consequences, and the second is the one that saves the round. Measure the window as its own step — create the fixture, poll it without touching anything, and record when it closes and what closed it (the journal usually names the worker, and it may well log the self-closure under the same event as the real thing, which is what makes it invisible from the outside). And once a window exists, restructure the scenarios that live inside it into **one scripted battery per fixture** — create, poll to the target state, fire every probe back to back, read the state after each — instead of a leisurely sequence of hand-made calls. Budget expendables accordingly: measuring the window consumes at least one fixture, usually two.

The same measurement pays a third time, outside the round: any existing automated test that drives this state is racing the same timer, and nobody has told its author. Report the margin in absolute terms — «the test spends 12 s of an ~80 s window» — because that sentence, not the window itself, is what makes a maintainer act. Precedent: a round was planned, briefed and case-documented on «the hung record waits indefinitely»; both seed fixtures closed themselves inside two minutes while the executor was measuring, a worker had been polling the third party all along and logging its own result as if the third party had answered, and the round's scenarios had to be rebuilt mid-flight into batteries — the executor escaped a false defect only because the brief made them re-read state after every refusal.

**A scenario whose main check needs an ALREADY-ELAPSED state** (an expired deadline, a spent quota, a lapsed reservation, a consumed
one-time code) **is planned only after one probe call proves the API lets you create that state.** Guards usually forbid it: writing a past
deadline is rejected, a counter cannot be set backwards. The plan then rests on a state that cannot exist, and the executor discovers it at
the main scenario rather than in recon. Two consequences for the brief: pair the scenario with an «observe the transition» variant (a
short-lived value plus a wait) instead of «set the past value», and say which of the two is the fallback. Precedent: a control run planned
as «differs from the main one only by the date» died on `400 must be after now`, and the round survived only on the spare «observe the
expiry, if cheap». The same probe also tells you the window of validity: a background job that clears elapsed values caps how long the state
stays observable.

*The mirror case: the state is elapsed by AGE and no call creates it — then the question is not what the API allows but how long the environment's data lives, and that is measured across EVERY environment before the plan is sliced.* Where the requirement is «the restriction on objects older than N was lifted», the fixture cannot be manufactured at all: age is not a field, and a create call has nowhere to put a past date. The only lever is an object that is already old enough, so the planning move is one read per environment — the oldest object of that class, sorted ascending — which takes a minute for all of them together. Shared test environments are commonly reseeded by their own deployments, capping the age of everything on them at days; where N exceeds that cap the requirement is unverifiable by construction, and the round says so in those words instead of passing its positive run off as proof. Two obligations follow, and the second is what keeps the verdict honest. Say plainly that a positive run on the available data **would have passed before the fix too**, so it is not evidence the restriction is gone — otherwise a green round is read as confirming exactly the thing it could not test. And carry any reading-based evidence as reading: name it, date it, and pair it with the single run that would close the question behind it. Precedent: a round on «the two-week limit on adjustments was lifted» found no object older than two days on any of five environments, every one of them reseeded within the week; the operation itself worked, the boundary stayed uncovered, and the verdict rested on the commit that deleted the check plus a retest protocol for whoever gets an environment with long-lived data.

**A requirement of the form «no more than N per hour / per day / per window» is planned against BOTH readings of the window at once — the sliding one and the calendar one — or a «there is no limit» verdict is unproven.** The two readings disagree about which call is the N+1st: a run that starts before the hour boundary and continues after it spends its budget across two calendar windows, so the call that is sixth by total count is only third in its own calendar hour. An executor who stops at the total count writes «no limit» while the implementation may simply have been counting the other way. The brief therefore carries the budget as a plan for both: reach N+1 by total count, and if that passes, reach N+1 inside one calendar window too — the extra calls are cheap next to a wrong verdict. Two companions to the same shape: **prove the calls were not silently swallowed** (the limit may be enforced by dropping the side effect rather than by refusing — check the artifact the call is supposed to produce, the email, the record, the message), and **decide where in the round the check goes**, because a working limit locks the account or the resource for the rest of the window and can strand the cleanup. Precedent: nine requests over 24 minutes all succeeded, three of them added purely to close the calendar-hour reading, and the delivery of the ninth artifact was confirmed separately — without those two controls the finding would have died on the first «you were measuring the wrong window».

**An oracle built on counting records in an external journal** (a webhook receiver, a delivery log, a queue) **is planned together with the
question «what is the journal's window»** — such a source usually returns the last N records rather than an archive. On a busy environment
your own record falls out of the window and the counter goes down instead of up: the assertion «there is one more record» turns red with no
defect behind it, and the cause reads neither from the code nor from the run log. The window is pulled with a single request, along with the
seam's contract. Precedent: the callback receiver returned exactly the last 100 records — the run had enough headroom, but the limit only
came to light at the executor, meaning the check rested on luck.

**A consequence derived from reading rather than observing is a hypothesis with an expiry date, not a finding — and the honest caveat does
not substitute for closing it.** «Effect computed from the served bundle / from the contract, not reproduced live» is the right label, but it
is where the work pauses, not where it ends: while such a claim sits in a report it is quoted, copied into the tracker and acted on. So every
derived consequence carries two extra fields — **what would close it, and what that costs** — and when the cost is one reversible pair of
operations, it gets closed in the same round instead of being labelled. Expect the live run to move the claim in *both* directions at once.
Precedent: a derived finding said the holder of an unrecognised role «can do nothing, every gated operation is refused, and the defect is in
the frontend». Live, under that role's own session: the server refused too (a separate, harsher finding), while «can do nothing» was false —
profile, vaults, balances, the member list and the audit feed all answered, and the UI degraded cleanly. Three days of the report carried a
claim wrong in two directions, each caveated.

**A scenario whose method of verification is unknown gets phrased as a question, not as a path.** «Walk to step X in the browser, wait, and
finish» shuts down the executor's search: they will check exactly that path, hit a wall and write «not covered». The same scenario posed as
«does the object have an externally observable oracle — and which one?» gets found right away. Precedent: an item marked in the plan as
«possibly uncoverable» was closed in full, but by an entirely different route than the plan assumed — and the guessing consumed the time
wasted on the brief's path.

**A scenario built on an UNUSUAL value — one that looks wrong, malformed or out of range — starts with the question «where does such a value come from in this system», answered on live data before a single scenario is sliced.** The intuitive route (a user or an operator types it in) is very often closed: input validation rejects exactly the shape the scenario needs, and the field turns out to be immutable afterwards, so the round discovers at the seeding step that its main fixture cannot be created at all. The cheap answer is one read of existing records grouped by the relevant attribute: the group that actually holds such values names the real source — an integration, an import, a provider's response, a legacy record — and that source becomes the seeding route. The same read also tells you which values are **reachable at all**, which turns a boundary scenario from «try 10, 15, 17 digits» into «only one shape exists in production, the rest are unreachable by construction» — a legitimate «not covered» that is a property of the system, not a gap in the round. Precedent: the plan sent the executor to create the value through the obvious user-facing operation; validation refused it on every type, the field proved immutable behind a silent `200`, and the real source turned out to be a provider's response — visible in one grouped read of the existing records, which the manager had not done. A quarter of the round went into finding that out.

**A scenario with expendable artifacts (sets of one-time codes, blanks, instances) produced by another step of the plan gets a fallback
table: which artifact goes into each subsequent step if the producing step fails.** A branch «if step X is rejected — do Y» without
reassigning the artifacts leaves the executor rewriting roles on the fly. Precedent, round 2: the plan expected «set B» from a reissue via a
recovery code, the reissue turned out to be the round's main failure — and every subsequent step tied to B1/B2 had to be replayed on codes
from other sets.

**A refusal observable only from a state that the action itself destroys is not checkable through the UI control — plan it on the API path or on a second carrier.** The shape: the control that triggers the operation is rendered only in state X, and the operation's first success moves the object out of X — so the negative («the same operation refused when the object is no longer in X») has no surface left to be pressed from. Written into the brief as a UI step it simply comes back «not covered», and the round loses the negative for free. Decide in advance: either the negative goes straight to the API (and then it is not a UI check, say so), or the plan budgets a second expendable object so one carries the positive and the other the negative. Precedent: the retry control exists only on a failed object; one click recovered it, and the documented refusal code could not be re-measured in that round at all.

*The same mechanism, one scenario over: a state-changing scenario can delete the surface ANOTHER scenario stands on, and then the damage is done by the ORDER of the plan rather than by a missing carrier.* The tell is a control whose visibility is conditioned on a state the round also toggles — a row rendered only while the object is enrolled, an action offered only in one status, a block shown only to a subscribed entity. Each scenario is sound on its own, so nothing in the plan looks wrong; the executor performs the toggle, moves to the next item, and finds the surface gone. Ask of every surface-reading scenario which state it depends on, and order the readers before the togglers — the reverse order costs the requirement its UI verdict and leaves the weaker «checked through the API» in its place. Where both orders are needed, budget a second object. Precedent: a plan put «remove from monitoring» before «change the risk level», and removal hides the risk-level row together with its edit control; the executor reordered the run on their own initiative and said so in their retro — had they followed the brief, a requirement graded spec-grade would have been verified only through the API.

**When the negative on a guard requirement SUCCEEDS, the round is only half done: measure in the same pass what the missing guard lets you reach through the product's own chains.** An absent guard gets written up as what it literally is — a value accepted, a record left inconsistent, a transition that should not have been possible — and priced as a data-quality defect. But a guard exists because the state behind it is privileged, and a state the object can no longer legitimately be in often re-enables operations the product had retired for it: a consumed one-time artifact becomes valid again, a completed step becomes repeatable, a spent allowance refills. One or two further calls down that chain decide whether the finding is a Minor about data or the round's Critical, so plan the chain as a conditional scenario from the start — «if the backward transition succeeds, immediately try the operations that the target state legitimately allows». Pair it with the rule that makes it affordable: every probe of that kind runs on an expendable the round created itself, never on an existing object, because the chain may well end in a state with no way back. Precedent: a backward status transition that «merely went through» read as a consistency defect until the registration flow was replayed with the original invitation artifact — it reset the password and the second factor on a live account, and the finding moved two priority steps up to become the round's result.

**A step that requires typing a financial or credential-shaped value is a HUMAN step — put it in the plan as one, before the executor hits the wall.** Registering a wallet or account, entering card, IBAN or account numbers, creating a payment reference: an assistant executor refuses these by its own safety rules, and no sanction from the user lifts that — the refusal is not about access, budget or reversibility, so it cannot be negotiated mid-round. The failure mode is silent until it happens: the plan reads as feasible, the executor spends attempts on two mechanisms (the API and the product's own form), and the round returns with its main precondition uncreated. Split such a scenario in two at planning time — «the user creates the entity» / «the executor measures on it» — and confirm the split in the start question. Note also what the boundary does NOT cover, because the useful half is usually large: reading an existing identifier and passing it into a call is ordinary work, and so is approving or activating an entity someone else registered. Precedent: a round sanctioned to create one wallet came back having created none — three refusals on two mechanisms — while every measurement that merely read an existing address went through untouched, in both rounds.

**When the condition cannot be reproduced, the first option you put to the user is «can you MANUFACTURE this state», not «may I mutate the live settings».** The instinct is to price your own route — a reversible mutation of a shared setting, with a snapshot and a restore — and to ask for permission to run it. But the user usually holds a cheaper lever the session cannot see: seeding a fresh tenant, running a provisioning script, resetting an instance. Put that first, in one line naming what state you need (not how you would fake it), and keep the mutation as the fallback with its price. Two questions of yours turn into one answer of theirs. Precedent: two rounds of «may I temporarily blank the shared configuration, snapshot taken» were declined, and the answer was «hold on, I'll register you one» — a purpose-built fresh tenant appeared in a minute, and the mutation was never needed.

**Claims in the task description of the kind «the rest was checked and is correct, no changes needed» are verified on par with the
requirements** — one cheap scenario each. The task's author checked the code, and the environment may answer differently; such claims are
not part of the DoD, so otherwise nobody will check them at all. Precedent: the description listed three adjacent distributions as correct —
control requests uncovered on two of them the very defect the task was fixing on the third (Major).

**A document referenced from the task may describe a DIFFERENT environment than the one under test — split it into scenarios and setup before planning, and say so in the brief.** A hand-written check-list or QA note attached to a task is usually authored against whatever environment its author had: a local stack, a developer's docker compose, a staging instance with its own hosts and its own seeded accounts. Its *scenarios and expectations* are portable and are exactly the value you pulled the document for; its *preparation section* — hostnames, `/etc/hosts` entries, build commands, mail catchers, seeded users — is not, and an executor who starts at the top will spend the first stretch of the round trying to reproduce a setup that does not apply. Say which half you are handing over, and make the mapping explicit where the document's names differ from the environment's. The same split protects the other direction: the document's «known limitations» were measured on that other environment, so they are claims to verify on yours, not facts to inherit. Precedent: a QA note attached to a task described a local docker stand down to the `make up` commands, while the round ran against the deployed one — the scenarios transferred whole, the preparation transferred not at all, and one of the note's «this is not a bug» limitations turned out to contradict an acceptance criterion of the task itself.

**When one scenario's SIDE EFFECT destroys another scenario's fixture, the order is load-bearing — and the plan has to say WHY, not just what comes first.** The shape hides in plain sight: two scenarios touch different requirements and look independent, but one of them sweeps state on completion — invalidating pending items, resetting a queue, closing open sessions of the same subject — and the other needs exactly such an item to survive for hours or days. Ordered wrongly, the second scenario is silently destroyed, often after the round has already reported the first as clean; the loss shows up as «the fixture vanished, must have been someone else's run». A bare «do A before B» does not protect it either, because an executor optimising their own pass will overlap them, or start B while A's pipeline is still draining. State the mechanism in one clause — «A fails every active item of this object, so B's fixture must be created after A has fully closed» — and the executor derives the rest, including the wait. Two riders worth the line. The same side effect is usually the round's **emergency exit**: whatever destroys the fixture can be re-run deliberately to clear it, which turns a multi-day artifact into something abortable, and that belongs in the report next to the artifact. And where the fixture blocks a shared resource for days, its cost is stated to the user before it is created, not after. Precedent: a round's two remaining requirements were a branch reachable only by acting outside the product and a timer measurable only over three days; the first fails all active requests of the contract, the second needed one to survive — the brief said «S5 before S6» with the reason, and the executor waited for the second pipeline to close before creating the long-lived fixture, on their own initiative.

**Overlapping operations on the same object are worth planning deliberately in any pipeline with deferred reconciliation — they are where its defects live.** Where a system confirms an operation asynchronously (waiting for confirmations, a worker pass, an external callback) and then reconciles the result against reality, the interesting question is never the single clean run: it is what the reconciliation compares. A second operation on the same object, landing inside the first one's confirmation window, separates the two implementations that look identical on clean data — comparing *the effect of my own action* versus comparing *the current state of the world*. The second is a defect, and it is invisible until something else moves the world in between. Plan the overlap explicitly (start operation A, then operation B on the same object before A settles) rather than serialising everything for tidiness, and say in the brief that a race is the point, not an accident. The payoff is largest exactly where the product's own headline scenario is a SEQUENCE of operations on one object — a rotation, a migration, a multi-step settlement — because there the overlap is not an exotic case but the normal mode. Precedent: a successfully executed on-chain operation was marked failed because the reconciliation read the current role state instead of its own transaction's effect; the defect surfaced only because two requests on the same address happened to overlap, and the product's target scenario was six such operations in a row.

### The main run and its control

**A scenario whose observation could mean two things is planned as a PAIR — the main run and a control differing in exactly one condition.** A single uninterpretable observation is not evidence, and the executor finds that out at the end, with the artifact already spent. Six recurring shapes, and in each the control costs a fraction of the main run.

**The documentation holds a branching rule** (amounts equal or different, role, status, entity type) **and the brief states one «correct» outcome** — then the first run down the other branch looks like a bug, and the executor spends a pass on a control experiment to tell a defect from the norm when they could have run both from the start. Precedent: a late callback expected to drive a disputed payment to success landed it in a different terminal status and read as lost money; a control run differing only in the amounts revealed the branching rule in the docs — by design.

**The artifact is CONSUMED by the first attempt** (a one-time link, a single-use code, a nonce) — then «it refused» cannot be told from «the artifact was already spent». Obtain the second artifact in advance or name how to reissue one, and say explicitly that re-trying the SAME artifact checks whether it was consumed, it does not repeat the experiment. Precedent: a refusal measured on a deactivated record looked like proof until the same link came back «invalid or expired» — the verdict became sound only after a second invitation was reissued and the control run on it succeeded.

**«Does the path work» is checked twice — on a fresh object and again on the same one.** One pass proves only that the path works in the first state, and the state the system reaches after a successful operation is often the broken one: a form that was not reset, a cached selection, a control whose state was not restored. Require a second consecutive pass with no reload and no new object, and apply the same rule when retesting someone else's `pass`. The flip side: **a defect found on the second pass is also checked on the first**, or «always broken» goes into the report instead of «broken after the first operation», and the developer will not reproduce it. Precedent: round 1 checked the «picked columns → got the file» path once and got a `pass`, having landed in the single working state; round 2 made six passes and uncovered a Major — after the first export is created, the column selection never reaches the server at all.

**The defect is non-deterministic** — budget for **a replica of the experiment that worked**, since without a repeat a single observation cannot be told from a coincidence, which is the question such a round asks; and require not «pick an outcome from the matrix» but **an updated list of live hypotheses with evidence** — the value is in the versions rejected plus one new testable hypothesis, whereas a ready-made matrix nudges the executor to pick a row and stop. Say in the brief that the replica is *also* the cheapest shot at a state you cannot induce: where the feature sits on a probabilistic mechanism the failure state is usually written off as «check the presentation on a substituted read», and if the replica lands on the real thing, switch to it and drop the substitution — a live failure buys the delivered event, the client's reaction and the positive path of the recovery control. Precedent: one round reproduced the defect twice, closed six versions of the mechanism and handed development a testable hypothesis, and no row of the original matrix described the result accurately; in another, the second of two replicas failed for real and closed the failure-state requirement live.

**A complaint of the form «type X does not work» is answered by a control carrying the SAME payload size in a type nobody complains about — otherwise the round confirms the complaint's own framing.** The shape arrives pre-diagnosed: a user, a manager or a support ticket reports that some kind of content is rejected, and the round is asked to reproduce it. What was actually observed is a rejection, and the kind of content is the reporter's hypothesis about the cause — usually the wrong one, because the property that correlates with the kind is size: a screen recording is an order of magnitude heavier than the pictures nobody complains about, and a transport limit cuts by bytes without ever looking at the type. Reproduce it and the round writes «confirmed, X is rejected», which is true and points the fix at the wrong layer. So build the fixture as a **matrix of pairs**: for every specimen of the suspect type, one control file of exactly the same byte size in the ordinary type, at both ends of the range. Two pairs settle it in four calls — agreeing at both ends means the type is innocent, diverging at one end names the type as the cause with the size held constant. The same construction generalises to any «it fails for values like this»: hold every property but the accused one. Precedent: a spike asked to confirm that video attachments cannot be uploaded; the pairs showed video and image of identical weight behaving identically at 8 MB (both accepted) and at 84 MB (both rejected), and the answer became a transport limit measured to 200 bytes — a reproduction without the controls would have sent a content-type defect to the team that owns the attachment handler.

**A filter that returns ZERO is a claim about the filter before it is a claim about the data — the control is the same query with the filter removed.** Absence is the cheapest finding to write and the easiest to get wrong: a listing answers `total: 0`, the requirement says such records must exist, and the round has its defect. But a filter argument has a *form* as well as a value — an id where a name was passed, a case-sensitive enum, a scope the caller cannot see — and a server that matches nothing usually says so by returning an empty page, not an error. The unfiltered control costs one call and discriminates instantly: records exist and the filter is wrong, or the collection really is empty. Run it before writing the row, and run it again whenever a filtered zero contradicts something you already measured. Two riders. The same control catches a filter that silently narrows more than asked, so it is worth the call even when the zero is expected. And a filtered zero taken from a *sample* you believe should be non-empty — «the approved ones must have some» — is the strongest trigger there is: that is exactly the shape a wrong argument form produces. Precedent: a query for an entity's checks returned zero for the target object and, in the same pass, for two objects known to have passed those checks; the finding «none of them has any» was one sentence from the report when the unfiltered control returned 568 records — the filter took an id and had been given a name.

**The oracle is DEGENERATE on live data** — the channel works and shows a value, yet two readings of it are indistinguishable because everything is zero, empty or equal by coincidence (a count or its price, a duration or a deadline, an id or an index). An executor who does not notice files `pass` and the requirement is lost silently. So for every scenario whose verdict rests on **what a value means** rather than on whether it is present, ask while slicing whether the environment's current values discriminate the candidates — and where they do not, plan the substituted read up front, with values chosen so each candidate would print something different. Precedent: «does this column print the token's quantity or its fiat value» was unanswerable because every token had both equal to zero; a substituted response with a quantity of 12.345 against a price of 99.99 settled it in one pass, and the answer (quantity, while the spec's example showed price) was the round's sharpest finding. *The cheaper variant of the same move, and the one to try first where the value is stored rather than computed: do not substitute a reading, FIND a record that discriminates.* A cross-consumer comparison — the same stored value read through two interfaces — is degenerate whenever live data holds one and the same value everywhere: every pair agrees, and a hundred agreeing pairs are equally compatible with «both read the same field» and with «both print the same constant». One grouped read over the collection names the minority values and the records that carry them, and a single pair drawn from there carries the whole verdict. Plan that read as its own step whenever the scenario compares two views of one value, and say in the brief that a comparison run only on the majority value proves nothing. Precedent: a round's cross-consumer check ran on records where the field was the same token in 192 of 200 rows; the executor sought out the owner of the eight exceptions on their own initiative, and the two pairs drawn from them were what made the other nineteen matches mean anything.

*The most degenerate oracle of all is «the state came back to where it started», because its expected delta is ZERO.* Scenarios about reversal — a refund, an undo, a rollback, a cancellation that releases a reservation — are naturally verified by comparing a snapshot taken before with one taken after, and the assertion reads as strong: every field equal, nothing drifted. It is equally satisfied by a product that did nothing at all, and that is precisely the failure such a scenario exists to catch. No tolerance, sample or repetition fixes it — the ambiguity is in the shape of the check, not in its precision. So plan a **third** observation: a snapshot in the intermediate state where the money, the lock or the record is supposed to be moved, taken between the two actions. Where the intermediate state is too short-lived to catch, name the indirect markers that only a completed round trip leaves — a counter of applied corrections, a terminal timestamp, the correcting record itself — and say in the brief that the zero delta means nothing without at least one of them. The same caution belongs in the report next to the verdict, because whoever reads the test later will read the zero as proof. Precedent: a reversal scenario asserted a zero delta across sixteen balance fields and passed; the verdict held only because the same run happened to carry the correcting record and the zeroed totals, and the round said so explicitly rather than letting the zero stand alone.

**A control that proves a guard has been LIFTED is attempted at once — immediately after the lifting action — because a manual pace hides the asynchronous window the next consumer will hit.** The pair is planned correctly (the guard refuses in state A, the same call must pass in state B) and then run at hand speed: the executor performs the lifting operation, reads a state back, writes a note, and calls the operation half a minute later. It passes, the control is green, and the report concludes that the lifting operation is what removes the guard. Often it is not: the visible state (the record's own status) flips synchronously while the guard reads something a background handler commits seconds later, so there is a window in which the thing is already permitted and still refused. Nothing in the round can see that window, because nobody was ever inside it. Say in the brief that the permitted call is fired **immediately** after the permitting action, before any other read, and that the interval between them goes into the result as a number; where it passes on the first attempt, the window is under that interval and the verdict says so. The cost of omitting it is paid by whoever automates the scenario next, at machine speed, as a red run they must diagnose from scratch — and by the round's own conclusion about the mechanism, which is drawn from a measurement that could not have refuted it. Precedent: a manual round left ~26 seconds between finalising a record and the call that finalisation permits, concluded the guard reads the record's own table, and published that; the autotest fired the same call three seconds after the same finalisation, got the refusal, and the trace showed the guard clearing only when the projection handler committed — the published conclusion had to be withdrawn from the report, the registry and the knowledge base.

*The same immediacy collides with IDENTITY: where the permitted call must be made under a different identity than the permitting action, the switch itself is inside the measured window.* A single browser profile, a single session store or a single API client serialises the two, so «fire the call immediately» becomes «log out, log in, then fire», and the round reports a window an order of magnitude wider than the real one — with no way to tell the product's asynchrony from its own login latency. Decide it while slicing: either the measurement gets a second isolated environment prepared in advance (a second browser profile, a parallel client already authenticated as the second identity), or the brief states that the interval is an upper bound inclusive of the switch and says so in those words. Precedent: a guard-lifting control came back «access returned within 95 seconds», of which about 60 were the mandatory re-login — the product's actual window was never measured, and the executor's retro asked for the second profile that would have closed it.

**«We will recompute what the product computes»** (a hash, a signature, a checksum, an aggregate, a fee) **is a coincidence of numbers until an independent consumer accepts the recomputed value** — the signature verifies under the key, the transaction reconciles against the chain, the total matches an external source. Require that half explicitly, or it stays the executor's initiative. **And where the product «threaded» an array — records per element, inputs, positions, rows — require a cross-control: substitute a neighbouring element's value and get a MISS**, since a match alone is compatible with an array filled formally with one and the same value. Precedent: two transaction inputs shared the same script, and without permuting the amounts a green result would have proved nothing; on the same round, verifying the MPC nodes' signature against the recomputed hash turned «5/5 matched» into cryptographic proof that the vulnerability was closed.

### Before a requirement is planned as «not covered»

**«We cannot verify this» is a claim about a fact, and every shape of it is settled by one cheap move made BEFORE the plan records the verdict.** The move differs — a question to the user, a manufactured carrier, a measurement of the nearest available operation — but the failure is always the same: a verdict about the round's own reach is written down as a property of the product, it costs the requirement permanently, and the next round inherits it unexamined. What such a row is allowed to claim once it is written is in `report.md`.

**«We have no access to X» is a request to make, with its price, not a verdict to record.** Where one channel the session lacks would close a requirement — an IdP console, a repository token, a database — name it in the start question: «read access to the identity console would close three of the four items in one pass». The rule holds even when the access looks unlikely; it costs one line in a question you are already asking. Precedent: three consecutive rounds recorded «not covered, needs the identity console», the user offered the access unprompted, and it closed every one of those items in a single read-only pass.

**Separate «there is no observation channel» from «the channel has nothing to show» — the second is manufactured, not recorded.** The channel works; the state simply does not exist yet — a role nobody holds, a status no record is in, an entity type nobody has created. Create a temporary carrier with a reversible pair of operations (grant then revoke, create then delete, set then restore), read the channel while it has something to say, and put the environment back; the test of applicability is that the operation has an inverse and the residue is bounded. Say what the probe cost and confirm the restoration by reading the state back from both sides. The flip side is what usually stops the probe: **«it might answer something other than what I expect» is not an argument against running it** — an unexpected resolution is itself a fact, and the only real arguments are cost and irreversibility. Precedent: three items were declared unverifiable for want of an admin console; one temporary role grant on an expendable account read the whole dictionary out of the orchestrator's sync payload, and the «muddy signal» that had been the reason not to probe turned out to be the round's main finding.

**«There is no way to do X» is not finished until you have measured what the NEAREST available operation does.** The absence of an operation with the right name is a fact about vocabulary; whether the risk is open is a fact about behavior, and only the second carries a priority. Take the closest thing the product does offer — deactivation, blocking, a status change, an expiry — and measure whether it closes the risk: if it does, the finding collapses to a Minor about naming; if it does not, the measurement turns a claim into proof. Precedent: a Major built on «an invitation sent by mistake cannot be revoked» survived exactly until the customer asked «and if I deactivate it?» — deactivation blocked confirmation completely, and all that remained was that the button is called «Delete».

**A whole screen is unreachable — establish WHERE the access decision is made before writing the round off.** The symptom is an unremarkable redirect while neighbouring screens open normally under the same session, and two mechanisms produce it: the server refuses (genuinely unverifiable), or the client alone decides and the server would answer perfectly well. The second is common on single-page applications and is discriminated cheaply — read the served bundle for the route's condition, and call the same data endpoints directly under the live session. Where the decision is client-side, the round continues with the guard neutralised locally under two conditions stated in the report: nothing that changes server state is sent, and every observation taken that way is «a check of the client, not evidence that the feature is reachable» — reachability stays closed by the blocker. Note for your own hands: neutralising a client guard may be refused by your own tooling even when it is legitimate, so plan it as the executor's step and verify the blocker yourself by the redirect plus a control screen that does open. Precedent: eight requirements were one redirect away from being written off; the guard compared the role name against a constant spelled with the wrong separator, and the round delivered a verdict on every one of them plus five further findings.

**A requirement of the «works under degradation» kind starts with «what will we use to induce it» — and the honest «nothing» is a full result, closed the right way.** The answer takes one call and closes half the plan, whereas scenarios sliced in advance look feasible right up to the run. No means of inducing it (no access to the cluster or pods, no product endpoint, no flag) → the verdict is **«not verifiable with our means»**; closing it with a positive run on a healthy system is not allowed, since a positive proves the absence of a regression, not the presence of a fix. The report then carries **the observable oracle you found** — which field or event will show the gate's result once the experiment becomes possible — and **a ready 15–20 minute retest protocol** for whoever holds the access. Precedent: the «M of N» gates live inside an activity and the participant set was found in three activities' payloads, but QA cannot take a node down — the session closed with a verdict on verifiability plus a protocol, not with a false «pass».

**The flip side: «this cannot be reproduced on the environment» is a hypothesis even when the fix's author said it.** It is verified on par with the requirements and goes into the brief as «do we have a means», with explicit permission to look for an unconventional lever (magic mock values, provider settings, flags): a developer routes around unreachability with access QA does not have — inserting an event into a queue, editing the DB — and therefore never looks for an external one. Precedent: «an auto-payment cannot be driven to Failed» was resolved by a mock provider's magic amount returning an expired deadline — 4 runs out of 4, through the real path.

**A scenario already blocked by a SANCTION still gets its fixture checked — otherwise the round asks for one permission where two are needed.** Once a scenario is parked behind a decision only the user can make (a budget for a paid call, permission for a destructive step), the manager stops examining it: the verdict is written, the reason is recorded, and the item reads as settled. But a sanction unblocks the *action*, never the *precondition*, and the two fail independently — the environment may simply hold no object in the state the requirement is about. The cost is paid a round later and in the worst currency: the user grants the permission that was asked for, the next round starts, and it stops on a second blocker nobody named. The check is the one already owed for any state-shaped scenario — does an instance of that state exist here — and running it on the parked items too costs one listing query. Say both blockers in the «not covered» row, and say plainly that two sanctions are required, not one. Precedent: a requirement about an operation being refused for objects in a terminal state was parked purely on cost; the executor discovered, from data the manager had already read, that the environment held no object in that state at all — so the next round needed a budget AND permission to move an object's status, and only the first had been requested.

**When a property of the environment makes a whole STATE unreachable, unfold which requirements die with it — and put them to the customer as ONE question, not as N rows.** A threshold, a setting or a degenerate configuration means some status never occurs: a request that reaches quorum on its creator's own signature never sits in «collecting signatures», an auto-approved entity never sits in «pending», a single-item list never paginates. The requirements attached to that status are scattered across the spec — an action available only in it, a transition out of it, a warning shown while in it — so the executor meets them one at a time and writes the same sentence N times. Name the unreachable state while slicing, grep the requirements for everything mentioning it, and the round gains one sharp question: «this contour cannot exercise these six items; either the configuration is part of acceptance, or the requirements need rewording». The knowledge to spot it usually already sits in your own recon or in a knowledge-base line about a neighbouring feature; the failure is not discovering it but failing to join it to the requirement list. Precedent: a threshold of 1 on the signing multisig collapsed the «collecting signatures» status entirely; six requirements depended on it, the executor discovered that six separate times, and the manager had both the threshold and the knowledge-base line in hand before the round started.

## Gates, budgets and the wording of restrictions

### The gate before an irreversible step

**A gate is a measurement taken BEFORE the irreversible step, and the brief must name the WAY to pass it — «make sure it is reversible» is not one.** Without a named mechanism the executor either invents one or goes ahead with reversibility unverified. The mechanism is the same in every shape: against the current, still unchanged state, perform the cheapest call that would have to work afterwards, and read what comes back.

**A reversible destructive action** (blocking, deactivation, revocation, a move to a terminal status) **is gated by a dry call of the REVERSE operation on the still-unchanged object** — a refusal or a dry run spoils nothing, while the response shows whether it is available to you and whether it demands something you do not have. One request, and it checks the permissions and preconditions on the way. Precedent: a dry call of the reverse mutation proved reversibility before the blocking and uncovered two defects on the way — the gate paid off before the main scenario started.

*Where the dry call itself is unavailable, the gate moves to a READING route — and a gate you cannot run is not a gate you may skip.* The executor's own safety rules, or the environment's, can refuse the reverse operation exactly as they refuse the forward one, so «dry-call the reverse» returns nothing and the round proceeds ungated. The reading substitute is usually stronger than the dry call anyway: find objects that have already made the round trip and read their current state and timestamps — a set of them sitting in the post-reverse state, with a modification time matching the reverse event, proves the transition is real on this environment rather than merely permitted to you. Say in the brief which form the gate takes, because an executor blocked from the mutation will otherwise report «gate not passed» and stop. *And the reading route proves the transition EXISTS, never that YOUR object may make it — check the reverse's preconditions on the specific object too.* That is the half that silently fails: the transition is ordinary, four neighbouring objects have made it, and the one the round is about to change carries an unmet condition of its own — an unreviewed queue, an open obligation, a dependency the other objects had cleared. The adjacent system states it plainly when asked (`GET` the object's related collection) and says nothing when not. Two consequences: the gate reads the object's preconditions, not just the transition's existence, and where the precondition is heavy — a hundred decisions someone must take by hand — the round learns before the destructive step that it is buying a one-way trip, which is a different sanction to ask the user for. Precedent: a gate proved `BLOCKED → ACTIVE` real on four companies and the round blocked a fifth; its unblock was refused by a guard requiring every screening match to be reviewed, and the object had a hundred of them, unreviewed since two weeks before the round — the environment kept the fixture blocked, and the requirement the reverse was supposed to measure went uncovered.

**An operation that TURNS SOMETHING ON — a pause, a lock, a maintenance mode, a feature flag, a freeze — is gated by a dry call of the OFF switch, performed while the thing is still off.** Such an operation does not read as destructive, so the round reasons about where the process might fail; and the dangerous failure is the one **right after the switch flips**, when the mode is on and the code that would turn it off never runs — a maintenance mode set before a migration that aborts, a lock taken before a job that dies. A refusal naming «nothing to turn off» proves the endpoint is wired; a bland success on a no-op is itself a warning that the switch may do nothing when it matters. No OFF switch at all → the operation is not reversible and needs the user's decision, not a plan item. Say plainly that failing to reach the end of the process is NOT the risk being gated. Precedent: a rotation flow was sanctioned with a gate against «it will get too far and strand the environment»; it failed on its first step, having already turned on a signing pause, and both documented ways to lift that pause returned success while changing nothing — the shared environment stayed frozen for hours and needed a database intervention.

**A scenario sensitive to COST** (a fee, a quota, a paid call, a consumable balance) **is gated on an already-created, still-unconfirmed entity**: «read the price there; threshold X — proceed, above it — do not confirm, record it and report». The gate turns «it didn't work out» into a measured verdict with numbers: in one session it stopped the run before 74 % of the wallet's balance would have gone into fees, and the round cost 836 units instead of 143 724. Two refinements without which it is fragile: **read the price as a series and judge by the worst observed case** (there it alternated between five discrete values from call to call), and **recompute the arithmetic against the facts at every step** — in that run the recomputation changed the decision three times and, after a cheap first step, removed the dependency on an unavailable tool entirely.

**A scenario whose expendable is spent BEFORE its precondition is known to be reachable gets a rehearsal on a free surrogate — an object of the same class that costs nothing.** The gate entries above protect against an irreversible step going too far; this one protects against it being pointless. The shape is quiet: the scenario reads «take an object in state X and do Y to it», nobody doubts that Y is permitted, and the cost sits entirely in *reaching* state X — a paid call, a consumed quota, an entity that cannot be deleted afterwards. The executor builds the fixture, spends the resource, and only then discovers that Y is refused outright for objects of that kind, so the expendable bought nothing. The rehearsal costs seconds and answers the only question that matters in advance: **is Y permitted at all**, asked of a same-class object that never entered the expensive state. Two consequences worth stating in the brief. The refusal text of the rehearsal is itself evidence — it usually names the real rule, which is often a product decision rather than a defect. And where the rehearsal succeeds, the scenario proceeds with the fixture's cost now justified. Precedent: a corner case about an event arriving for a deleted subject burned a paid vendor session before the deletion was even attempted — the subject turned out to be undeletable by class; the executor then invented the rehearsal themselves, on a subject created without the paid step, and got the answer in ten seconds.

**A dry call of the REVERSE operation is a gate only where the reverse is already legitimate — where the forward step is what creates the reverse's precondition, the reverse is obliged to fail, and the gate becomes a comparison of failure SEMANTICS against a control.** The reversibility gate above is written for a reverse that is valid right now: unblock what is blocked, revoke what is granted. A large class of destructive steps is not shaped that way — the forward step brings a thing into existence (adds the member, creates the record, grants the entitlement) and the reverse can only act on what the forward step produced. Dry-called beforehand it is refused by construction, so a brief that says «revert on the dry call → stop and report» stops the round on the one outcome the gate was always going to produce, and an executor following it literally delivers nothing. The repair is one control call and it is stronger than the original gate: run the same reverse against an object that is already in the target state, and compare the two failures. Different codes or messages mean the first refusal was an unmet precondition and the operation itself is available; identical ones mean the reverse is genuinely unavailable and the gate has failed. Where the failures are opaque (an unverified contract, a bare error code), the comparison is still the discriminator — the codes differ or they do not. So phrase this gate as «a refusal whose semantics differ from an unmet precondition is a stop», name the control object, and say that a bare refusal is not by itself a stop. Precedent: a gate demanded simulating the removal of a member before adding them; removal of a non-member necessarily reverted, and the round was saved only because the executor invented the control themselves — the same call against an existing member returned a different error code, which proved the operation available and the precondition merely absent.

**Where the round's decisive action is performed in an ADJACENT system, the preflight checks THAT system's own preconditions for it — not only the object's state.** The plan's attention goes where the round's risk feels concentrated: reaching the neighbouring system at all, keeping its session alive, getting the sanction for an irreversible step. All of that can be in hand and the action still be refused, because the neighbouring system gates it behind a condition of its own — a prior process that must have finished, a queue that must be empty, an item that must be reviewed first. That condition is invisible from the object's status (the object looks exactly like one that is ready), it is usually one read away in the same session the preflight already holds, and discovering it at the action costs the most expensive minutes of the round: the sanction is spent, the user is at the keyboard, and the fixture may have to be swapped. So when slicing, ask of the decisive action «what does the other system require before it will accept this», and read that in the same pass as the object's state. Two riders. The condition is often satisfiable in-product by a cheap action of the same system (re-run the prior process), so the answer is not necessarily a blocker — but it is a step, and steps belong in the plan rather than in the run. And a condition that has been **stuck** rather than merely unmet is a finding in its own right, usually about the neighbouring system: nothing in either product announces that an object can no longer move forward. Precedent: the round's whole point was one status decision in a compliance system; access was live, the sanction was given, and the decision was refused because the object's screening had hung unfinished for twenty-five days — one read of the screening list at preflight would have moved that discovery before the plan, and the hang itself became a Major finding for the neighbouring team.

**A gate proves permissions, not the recording of the result.** A dry call shows that the form opens and the rights suffice; it proves nothing about whether the platform will register the forward step. So the destructive step counts as finished only when the request reaches a terminal status, and the mismatch «executed in the external system, the platform says failed» is a signal to stop immediately rather than continue down the plan. Second half: **say what to do when the rollback turns out to be impossible through the product's own fault** — record it, report it, do NOT repair it by a workaround that bypasses the product, and state in the report that the cleanup was not done and what it will take to restore the state. Precedent: the gate passed, yet the rollback was blocked — the platform marked as failed a transaction that had really executed, and the environment stayed changed with no in-product way back.

**A gate that stops the run is not a ban on initiative.** «Gate not passed → stop and report» reads as one: in one session the executor knew a project-proven technique (substituting the *read* of the calculation plus one click) that rescued the round, but did not apply it on their own, and the approval round trip cost time. The phrasing: «if the target step is blocked by cost or by the environment, look for a legitimate workaround to the same proof that does not distort the branch under test, and propose it before declaring a gap in coverage» — a workaround that changes the logic under test stays forbidden. The same instinct applies to every restriction in a brief: **phrase it as «by default», never as a ban**, or it eats coverage where widening would have cost nothing. Precedent: «subscribe the receiver only to such-and-such channels» read as a ban and left a neighbouring requirement unverified at zero cost of verification — the executor closed it only by deliberately departing from the restriction. The phrasing: «by default X; wider — if that closes a requirement and does not dirty the environment, with cleanup in the same round».

## A round with a step only a human can perform

Some checks end at a wall the executor cannot pass: signing in a wallet, confirming a transfer
of funds, creating an account, entering payment details. Those become an instruction for a
person, and the instruction is a deliverable of the round like any other.

Before handing it over, **check the tracker for open defects in exactly that area** and put the
warning inside the instruction. The person following it has neither the session nor the
findings registry, and a known-broken precondition turns their action into damage rather than
evidence.

Precedent: a round parked wallet delegation as a customer step. Reconciling findings with the
tracker afterwards surfaced an open defect (in code review, not deployed): the form caches a
contract address from page load and never re-reads it, so delegation had already gone to a
third party's address four times for a substantial sum, with no signal to the user. Had the
instruction gone out as first written, the customer would have signed under the same
condition; as amended, it opens with «hard-reload the form before signing».

Same shape, other addresses: an operation whose target entity was renamed since the last round,
a form whose validation is known to accept bad input, a flow with an open data-loss defect.

### The human's instrument has PROPERTIES, and they decide how deep the round can go

When the round's decisive step runs on a device or an account **the user owns** — a phone, a hardware key, a personal wallet, their own mailbox — the start question almost always asks the wrong half. «Will you take part» is answered «yes», the plan is sliced around a full run, and the property that actually gates the depth (which identity that instrument holds, which network or tenant it is pointed at, whether it carries a test account or a real one) surfaces only when the executor is already standing at the pause with the whole branch prepared. Then the round splits in two on the spot: the observation half still works, the acting half has to be re-addressed to another carrier, and the brief that ordered it is wrong in the middle of a run.

The fix costs one clause in the question you are already asking: name the property the plan depends on and ask for it **by value**, not by capability — «which address does the wallet on that phone hold», «is that mailbox the one the account was registered with», «which tenant is that console logged into». Ask it before slicing, because the answer usually moves scenarios between carriers rather than removing them.

Two riders. The answer may also be a **boundary the round must not cross**, and that is a result, not an obstacle: an instrument that turns out to be the user's personal one is used for observation and never for signing, paying or sending, whatever the plan said — say so plainly in the report, since «not covered» here is a deliberate choice, not a gap. And the acting half is rarely lost: the same action usually has a second carrier the session already controls (a test account in another client, a scripted signer, a second profile), so name that fallback in the plan instead of discovering it mid-round.

### The wall is sometimes in the environment, not in the product

The step a human must take is not always an action inside the product. It can be a condition of
the **environment the product is observed through**: which browser extensions are installed and
enabled, whether a profile is clean, whether a physical device is attached, whether the page is
served over an insecure origin. An executor driving a page can add to that environment but
usually cannot take away from it — it can declare one more provider, not silence a real one, and
the browser's own settings pages are out of reach.

The damage is quiet and it is collective: a single unreachable condition takes out **a whole
family of requirements at once** — every clause phrased as «exactly one», «none at all», «after
removing the remembered one» — and the round discovers this at execution time, one scenario
after another, instead of at slicing time. Precedent: seven clauses of one spec, a quarter of
its acceptance criteria, all died on the same wall — the executor could not disable a browser
extension — and each was found separately, mid-run.

So while slicing the plan, ask of every scenario what it needs **removed** from the environment,
not just added. Whatever needs removing is a customer step from the start: it goes into the plan
as such, into the brief as such, and into the report's «not covered» with the environment named
as the reason rather than the executor's reach.

And when a requirement depends on an **event the environment has to deliver** — «the list refreshes
when a component is installed», «the banner appears when the device reconnects» — plan the control
that tells apart the two ways it can fail: the event never arrived, or it arrived and the product
stayed silent. Only the second is a defect, and without the control the round reports the first as
if it were the second. The cheap form is to split the requirement in two: the **reaction** is
verified by synthesising the event (an announcement made from inside the page, a forged callback),
and the **real source** is verified separately, or honestly recorded as not covered. Precedent: a
round watched an open page for six minutes after the customer re-enabled a browser extension and saw
nothing change; the control showed the platform had never announced itself to that tab at all, so
the reaction had nothing to react to — measured earlier on a synthetic announcement, it worked in 26
milliseconds. Reported without that control, it would have been a defect against the product.

## A checklist item carries the framing its finding will inherit

A regression checklist grows from two different sources, and they are not interchangeable: a
**requirement** (a spec clause, an acceptance criterion, a matrix row) and an **observation** (how
the product behaved last time, usually recorded in the knowledge base). Written down side by
side they read identically — one line of expected outcome — and by the time an executor measures
against the line, the difference is invisible. Then a finding is filed as «violates clause N»
when clause N never said that.

So, while writing the item:

- **mark the source of the expectation** — a requirement (with its address) or an observation;
- for an observation-derived item the expected result is «the behavior has not changed», and a
  mismatch is a **question for the analyst**, not a defect against the spec;
- before assigning a priority to any finding, re-read the clause the item cites **verbatim**, not
  the item's paraphrase of it. A matrix of who-may-see-what says nothing about what the screen
  contains.

And run the check «is there a requirement for exactly this carrier» over **every** finding of the
round as a list, not only over the ones that happened to raise a doubt. The dangerous case is the
finding whose framing came from your own plan, because it arrives pre-justified.

Precedent: a plan item read «view the fields **and the status**», with «the status» lifted from a
knowledge-base line describing the previous implementation. The spec clause it cited was an access
matrix — «view the profile: R for three roles» — silent on the screen's contents, and satisfied.
The finding went out as a Major regression against that clause; the customer asked «is there a
requirement for that at all?», and it had to be requalified to Minor with an analyst question, along
with every derived artifact. In the same round the identical rule was applied correctly to another
candidate — the difference was that nobody's plan had pre-framed that one.
